# Cycle 004: 未見課題の自動比較と中断成果の保全

共有JSONローダーの重複キー拒否を、新しい実需要の課題として実行した。
[課題・予算・介入](protocol.md)と22項目のテストは、両条件の開発前に固定した。
初期コード、image、cache、モデル指定を揃え、コマンドのnetwork権限だけを変えた。
正しい参照実装と故障を入れた実装で評価器を校正し、実Dockerを含む15テストを通した。

[自動比較結果](small-comparison.md)／[機械可読の全観測](small-comparison.json)／
[実行と校正の証跡](provenance.json)を参照。人やLLMによる採点変更、モデルのやり直しはない。

- 対照の提出物は22/22合格。終了コード0・使用量ありだが、停止処理込みで
  1,200.873秒を記録し、固定した1,200秒の予算条件は不合格。
- 改良はcheckpoint保存後の`docker unpause`が60秒でtimeoutし、中断した。
  正確な終了時間と使用量は欠測。1,200秒の予約分の計上を実測値に見せない。
- 両containerの停止を確認してから、対照の提出物と両条件の記録済みcheckpoint、
  改良の停止後に保全した成果の計16点を、元の22項目で採点した。
  改良の保全成果も22/22合格だが、正式な提出・予算内完了には昇格させない。
- 120秒を指定した観測は、対照120.198秒で13/22、改良120.145秒で22/22。
  その後の観測は実際の取得時刻がずれる場合があり、JSONに実時刻を残す。
  この1組から一般的な品質向上や高速化を結論づけず、最終の速度比は算出しない。

一括実行は完遂できなかった。中断は未完了として保持し、後処理を追加して採点を閉じた。
新しい[中断成果の評価入口](../automatic/finalize_interrupted.py)は、実際の停止証拠を必須にし、
元のstateを変更せず、独立した保存先へ観測を出す。元の評価器・基準・archive hashを検証する。
保全成果が合格しても、提出・既知の使用量・速度比較の成功に変わらないことを4テストで確認した。
これは開発再実行や、採点後の条件変更ではない。

## 実用コードへの反映

対照側の共有ローダー、回帰テスト、説明を`e3be833`で統合した。
両実装は固定機能条件を満たしたが、対照側はエラーへ入力キー自体を埋め込まず、
診断の長さが巨大なキーへ比例しない。これは統合上の判断であり、元の比較得点は変えない。
単一object内でdecode後の名前が重複すると拒否し、別objectの同名キー、通常の型、
非有限数拒否など既存の動作を保持する。依存の追加はない。

配布時の検査は[installed_duplicates.py](installed_duplicates.py)で行う。
通常・frozen image内のagentctl、duration atlas、project validator向けの3配布物を対象に、
統合sourceのhashと22項目を照合する。外側でmountを記録し、runtime sourceを重ねない。
配布検査は開発時間・固定比較得点から分離する。

[統合の検証結果](integration.json): 契約・CLI・job・supervisorの138テストが合格。
候補が未解決としていたF07 fixtureも10/10で合格を確認した（候補内の不一致記録は保持）。
通常・frozen build、Mira hook、両imageの既存CLI各42テストが合格。
両imageの3配布先それぞれで22項目、各image計66項目が合格し、source hashも一致した。
故意に期待hashを変えると、機能の66項目が通っていても配布を不合格にすることを確認した。
中断処理・表示・評価器の最終回帰は計8テストで合格した。
