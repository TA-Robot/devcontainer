# 次の比較: 同じ強い成果物を引き継ぎ、その先を改善する

2026-09-09。次milestoneの設計判断。live protocol・開始台帳ではなく、新しい実行はまだ登録していない。
ownerはprimary/integrator。今回の3開始は[result.md](result.md)で閉じた。

## 変える問い

「白紙から40分で、協働が単独より良いものを作るか」から、
**「既に強い成果がある開発で、単独が残した不足を、協働によってさらに改善できるか」**へ進める。
題材と品質vectorは維持する。満点に近い小課題や、回収だけの評価へ戻さない。

今回も3条件が基礎dispatch、予約、cache対応、比較用harnessの開発をそれぞれ行った。
強い単独の最終成果に両協働が届かなかった以上、単に相談指示をさらに長くする根拠は薄い。
現成果を共通に引き継ぎ、残る失敗の探索・反証・改造・統合へ開発枠を使う案を優先する。
基礎実装の重複が敗因だったと確定したわけではなく、時間配分は次に確認する仮説。

これは課題の出発状態を変える能力探索であり、今回の指示介入の追試・救済とは分ける。
通常の継続開発に近づける意義もあるが、出発点を強くすれば必ず協働差が現れるとは仮定しない。

## 共通の出発点と対照

1. 今回の単独の封印済みsourceを、両条件へ同じ初期実装として渡す案を第一候補にする。
   SHA256は`24c82c7e2fbc98edb73a384170074da8bf0240eb5203179aa253cbe9a5055424`。
   元artifactを編集せず、新しい開発コピーを作る。読み込み能力・実行制約の校正後に採否を固定する。
2. 単独にも同じsourceからの継続開発、別方式への置換、複数案、自己検証、再考を許す。
   元の単独得点は基準点であり、追加開発をしていない固定対照にして協働を有利にしない。
3. 協働は標準のnative能力を持ち、独立の反証、別実装、相談、統合を不足に応じて選ぶ。
   未達だったrefinement指示の通常採用は行わない。今回まず比較するのは継続開発での到達力。
   後に指示の改良効果を問うなら、同じ協働能力・出発点の改良前後を別に揃える。
4. 共通に渡す説明は公開contractと初期sourceの使い方・公開検証に限る。
   評価入力、seed、評価側のtrace、他条件の会話、今回の非公開ケースの正解手順は渡さない。
   公開上の説明を追加する場合も両条件へ同じbytesを渡す。
5. 初期実装そのものも、新しい固定評価入力で非agentの基準として採点する。
   両developer終了・提出固定後に行い、差分をdeveloperへ返さない。過去と入力の異なる得点を引き算しない。

## 開始前に具体化する有限作業

- 既存の回収・採点経路に、初期sourceを両条件へ同一に配布する最小の接続を別版で作る。
  旧runnerは変更しない。新しい汎用開発studio、全方式の総当たり、常駐agentを前提にしない。
- 疑似providerで、初期sourceの読込み→編集→公開失敗→修正→提出原文封印を両条件で確認する。
  単独のsubagent非公開、協働の全参加者終了、usage不足と品質の分離、評価側への境界を保持する。
- 新しい公開/採点入力、実行順、全開始本数、時計・output・採点・外側の全予算を事前固定する。
  まず各条件1開始をplanning priorとするが、これは現在の開始許可枠ではない。
  source一致の校正と有限protocolができるまでliveは開始しない。失敗時の追加枠を設けない。
- 主品質は最終成果の期限内価値・最重要完了と負荷帯別退行。初期sourceをどれだけ改善したかも併記する。
  未完了量・打切り・応答標本数・実行資源・全参加者usageも残す。完了件数や改変行数を成果にしない。

40分・16万output・同一CPU/memoryを引き継ぐかは、継続開発の公開能力と校正を見て開始前に決める。
現時点ではplanning priorであり、固定protocolになった時点で当該runの上限とする。
別のseedを新しい課題系列や未使用confirmationと呼ばない。基準点は現在の既知成果であり、世界最適でもない。

## この案への批判と停止条件

| 懸念 | 扱い |
| --- | --- |
| 初期sourceへのanchoringが強まり、別解を見失う | 両条件で全面置換・独立案を許す。実際に何が変わったかをsourceと公開反例で診断する |
| 単独を長く走らせれば同じ改善が出る | 同じ初期source・追加予算の新しいstrong soloを対照にする。元得点だけとの比較を主結論にしない |
| この課題に協働が有利な残余がほとんどない | 満点との差を根拠にしない。継続後も協働で変わり得る不足が示せなければ、題材適格性を再検討する |
| 局所修正を重ねても品質が動かない | 新しい反例・挙動差・有望な試作が増えない対話を止める。人数と会話回数を追加する既定にしない |
| starting stateを変えて勝つまで実験するだけになる | 本数・採否・欠測処理を先に固定。今回の負の結果を残し、継続開発という別の問いと明記する |
| 費用欠落が続く | 正常提出の品質を回収し、token上限適合・費用効率は引き続き保留。費用修理を品質改善と数えない |

次milestoneの完了は、共通初期source・両条件の能力・情報境界・予算を実行可能な別版へ固定し、
疑似providerで確認できた時点。そこで登録する有限比較の結果までを次の能力判断に使う。
この設計文書自体をハーネスの品質改善や能力拡張の達成とはしない。
