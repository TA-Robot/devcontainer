## 何が変わったか

旧版の「全jobと所要時間が既知の小規模な割当」から、継続到着、締切、価値の異なる仕事、
共有memory、cache費用、未知の処理時間、workerの停止・復帰を含む開発課題へ広げた。
未来情報を持つ評価側が時計・資源・得点を所有し、方策には公開された現在/過去の観測だけを渡す。
旧source・得点・confirmationは変更していない。

## 結果

各セルは **期限内完了価値 / 最重要クラスの期限内完了率**。各帯の8例を分子・分母で合算した診断値。
case別・class別・費用・未完了の値は[calibration.json](calibration.json)に全件保存した。
この合算値だけで主比較の合否を判定しない。

| 方式 | 96 jobs / 6 workers | 288 jobs / 8 workers | 768 jobs / 12 workers |
| --- | ---: | ---: | ---: |
| FIFO | 66.8% / 61.8% | 35.7% / 30.3% | 8.1% / 6.5% |
| 締切優先 | 69.5% / 67.3% | 48.7% / 52.4% | 14.4% / 17.5% |
| 依存先の価値を考える密度順 | 75.9% / 74.5% | 64.4% / 72.4% | 53.0% / 69.4% |
| 複数workerの配置をbeam探索 | 79.2% / 78.2% | 70.1% / 79.3% | 60.9% / 79.9% |

重い負荷でも方策により保護できる仕事が大きく変わる。
配置探索の最重要クラスは418件中334件を期限内に完了し、84件が未達だった。
ただし残る84件の全てがonlineで救えるという証拠ではない。
負荷の過大さ、期限の実現可能性、方策の探索不足はまだ切り分けていない。

配置探索は帯の集計では最良だが、各caseの総価値では他方式に1〜4だけ負ける例もあった。
これは方式の大きな得意領域の分離を示すほど強い逆転ではない。
今回の4方式は単純規則と局所的な配置探索であり、強い最適化の限界を示していない。
内部名`lookahead`は配置のbeam探索を指し、未来到着を知る解や長期rolloutではない。

## 採否と次の有限作業

動的課題と広い負荷帯の実行評価は成立した。ここで別題材へ移ったり、さらに機能を増やしたりしない。
次はこの課題で高い成果水準とstrong-soloの探索を結ぶ。

1. 現在の4方式を最低限の対照として保持し、現在までの情報で先の実行計画を比較する強い参照を加える。
   未知の未来を使う参考限界は別扱いにし、期限/容量だけで不可避な未達を難度へ数えない。
2. 重要な仕事の保護と他クラスの処理を両立する、到達根拠のある品質水準を固定する。
   今回の配置探索のvectorをそのまま新しい満点にして、旧版の低い天井を繰り返さない。
3. 動作契約・品質水準・開発tool・全予算を固定し、広い負荷帯を一つのstrong-solo開発でまとめて評価する。
   容易な帯から順番にliveを繰り返さず、実行失敗と意味ある品質未達を分けて協働探索の入口を判断する。

現時点ではlive開始枠を消費していない。適切な難題としての採用は未確定だが、
旧版の参照方策に到達するだけの評価から、競合する仕事の品質差と未達を測れる評価へ進んだ。
