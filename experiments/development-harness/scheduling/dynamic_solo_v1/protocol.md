# Dynamic strong-solo quality profile: one initial start

Scope: one fresh gpt-6-astra/high developer session using pinned Codex CLI 0.153.0.
This is continuous-quality exploration before a collaboration comparison, not
proof of stable solo inability or a pass/fail SLA. The old two-start static
protocol is closed and is not reused. No other model/agent, retries or second
developer start belong to this protocol.

Question: after substantial redesign and self-experimentation, where does a
strong single developer's selected online policy land across the full dynamic
domain, relative to the already-fixed joint-assignment beam reference?

Primary reporting unit: a full developer episode, not individual scenarios.
Retain each of the 24 qualification cases and the twelve family/band groups.
Report on_time_value/offered_value AND weight-16 on-time count/total; report
unfinished value, deadline deficit, completed-response tail/sample count and
busy/interrupted/unfinished work. Do not hide a critical regression in a total
value improvement. Reference comparisons are diagnostic; no per-cell best-of,
new post-hoc threshold or selection of favorable groups creates a pass.

Developer information: public TASK and transformed historical runtime contract,
24 development cases, editable workspace, Python/shell, FIFO, trace-producing
public checker and one tiny smoke example. No authoring generator, reference
code, prior candidate, qualification input, prior private result, authoring
checkout, Docker socket or another developer context is mounted. Own generated
tests and non-agent algorithmic search are allowed. External grades are never
returned during development. One self-selected source of at most 64 KiB is graded.

Budgets fixed for this single start: 2400 seconds development, 80000 observed
output tokens; each of the submitted-policy and fixed-reference assessments at
most 900 seconds. Total outer cap 4500 seconds reserves preparation and cleanup.
The development time is a planning prior: 24-case public checks cost roughly
1–2 minutes for current policies, so 40 minutes permits several redesign/test
cycles. Token/runtime/container limits are cost caps, not estimates of optimal
agent budgets. Owner: primary/integrator, scope: this initial profile only.
No automatic extension or retry if the envelope proves insufficient.

Live actor: one CPU, 2 GiB, 256 PIDs, fixed image, workspace-write shell sandbox
with networking disabled, no native subagent tools. Parent CLI alone uses
existing provider authentication. Public checker and CLI share actor resources;
external policy has one CPU and 256 MiB. CPU/memory differences are disclosed.
The actual CLI must pass provider-free shell edit/repair/network-denial/tool
surface checks on matched source before live. Independent grading and copied
submission/seals must be verified. Temporary credential copy is removed.

Incomplete usage, deadline/capacity/infra failure or unknown cleanup withholds
quality interpretation. Missing/invalid submission remains a recorded outcome,
not a successful completed policy. Do not replace it with an earlier candidate.
Known output token usage is checked at final completion; exact streaming token
enforcement is not claimed. Record input/cached input/output separately; root's
planning/implementation/review usage is outside the measured episode and unknown.

Freeze source, public projection and evaluation before starting. The qualification
population is the unused new dynamic population; a fixed non-agent reference is
evaluated on exactly the same cases AFTER the developer terminates. It is not an
advisory agent. No confirmation population is generated or assessed.
After inspection, qualification is known exploration data and cannot be relabelled
untouched confirmation. Record successes, failures, source hashes and all starts.

Interpretation: broad attainment/gains may disqualify a weak difficulty claim;
meaningful gaps suggest hypotheses about exploration/selection/robustness but do
not prove causality. Overload is not intellectual difficulty. Joint feasibility
and online attainability remain separate from optimistic necessary bounds. Fix
any later collaboration comparison, quality criteria and budgets separately.
