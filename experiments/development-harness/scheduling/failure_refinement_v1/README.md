# 共通する失敗から候補を改良する協働指示

2026-09-09。`adaptive.md` は次の H4 介入候補。live 実行・効果検証・通常配布は未実施。
[公開記録の診断](../public_frontier_v1/result.md)を根拠に、選択支援だけを先に作る計画を変更した。

## 変える行動と仮説

既存の [adaptive 指示](../adaptive_pair_v1/adaptive.md)は独立案・相談・反例・統合を許可しており、
前回もそれらは実行された。単に「もっと相談する」と強調する介入では不足する。
新版では次の仕事を**現在の失敗と候補間の違い**から選び、別案も同じ所で失敗した場合は
共有する前提を変える試作へ進める。初期の独立探索も許し、反例を用意するまで相談禁止にはしない。

期待する mechanism は error decorrelation と evidence-producing refinement。
別実装を作る際の初期の情報境界で anchoring を減らし、その後は反例・実測・変更済み source を
共有して改善する。観測した差がなければ、役名だけを増やして続けない。
探索、反証、採否、統合を root が所有する。人数や交換回数の固定は追加しない。

これは「13 記録にない優れた候補を生む」ための仮説であり、過去の失敗原因の確定ではない。
新しい統合で上限を越えられる可能性もある。CPU 競合、時間配分、実装上の偶然も代替説明として残る。
指示を長くすることで、報告・局所修正に偏り探索を狭める risk があるため、記録様式は新設しない。

## 比較へ進める条件

1. 新版の実行経路で、終了した提出物の封印と quality / usage / budget / cleanup の状態を分ける。
   usage 欠落時も選択済み source を保全する。費用不明を費用適合や正式な比較成功にしない。
   修正はこの比較に必要な回収経路に限定し、過去の actor / pair を変更しない。
2. 同じ協働能力を持つ旧指示と新版を比較し、同じ新しい課題入力で strong solo の基準も保つ。
   両協働条件の tools、CPU、memory、model/effort、開発時間、公開情報は同じにする。
   公開実験の補助を追加するなら両協働条件と solo に等しく配布し、今回の指示介入と混ぜない。
3. 新しい入力・全開始本数・順序・全予算・欠測時の扱いを別 protocol で固定し、source と一致する
   provider-free 検証を残してから実行する。この directory は live 開始台帳ではない。
   既存 24 ケースは方法選定済みの探索用であり、新しい confirmation と呼ばない。
4. 実際の最終成果、重要 class の退行、全負荷帯、回収できた全 usage を評価する。
   保存候補の上限や対話量を最終成果へ置き換えない。改善なし・欠測もそのまま採否に使う。

40 分と 16 万 output は旧条件を引き継ぐ planning prior で、owner は primary。
新 protocol に採用した時点で当該 run の cost cap となる。校正で実行時間・回収能力が成立しなければ
開始前に見直す。4 slots は現 native runtime の capacity に由来し、人数の推奨ではない。
将来の model 変更も比較前に両側で固定し、会話中の呼称から実行 model を推定しない。

[新版回収経路](../native_recovery_v1/README.md)は実装し、source一致の7試験を実CLI＋疑似providerで通した。
usage欠落と観測output超過でも正常な提出物を独立採点し、費用・予算の保留を維持できる。
これで上記1のactor単位の校正は完了した。
[refinement_cohort_v1](../refinement_cohort_v1/README.md)で全条件の封印barrierと新入力・開始台帳・protocolも固定し、
source一致の6試験と公開24例の校正を通した。次はこの固定cohortで実比較する。
この接続の完了も能力拡張の達成ではなくH4の検証準備である。
