# 目的から見直した次の品質介入

2026-09-09。直前に提案した回収修正・選択支援も含めて、目的から優先順位を見直した。
実験内の model は protocol に記録された gpt-6-astra/high のままである。
以下の「判断」から「次の実行順」は開始前のレビューとして残す。
同日中に[3条件の実比較](../experiments/development-harness/scheduling/refinement_cohort_v1/result.md)まで完了した。
実施後の判断は末尾へ追記する。

## 判断

主目的は、強い単独が見つける・選ぶ・統合する能力を、協働で拡張すること。
最新の一組はそれを示していない。自動評価の回収不足は直す必要があるが、
回収を完全にしても成果物の品質差は改善しない。

直前の「まず回収を直し、その後に選択支援を作る」という順序を修正した。
保存済みの公開実験から候補集合を診断したところ、**結果を知った上で最良候補をケースごとに
選ぶ上限さえ、単独の公開成果を下回った**。全24例が揃う13記録で価値11,521・最重要565、
単独は11,607・581。独立採点ではないため、記録の追跡性を分けた
[診断と限界](../experiments/development-harness/scheduling/public_frontier_v1/result.md)を残した。

この候補集合に対しては選択支援だけでは不足する。次の介入を、共有する失敗の反証と、
より良い候補の生成・新しい統合へ変える。順位付けの改善余地自体を否定はしない。

## 別の角度からの批判

| 観点 | 今回の証拠と問題 | 今回の判断 |
| --- | --- | --- |
| 課題の難しさ | 強い solo は多数の試作・自己検証を実施。severe には未完了があるが、一部は容量不足 | 満点との差を改善可能量としない。動的課題は探索題材として保持し、難題適格性は未確定と明記 |
| 候補生成 | 協働の全記録を都合よく選んでも solo の公開成果以下 | 既存候補の選択だけより、新たな実装・統合を生む介入を優先 |
| 独立性 | 両条件とも予約と dispatch へ到達。協働には独立案や反例もあった | 解法名の一致だけで同一性、役名の違いだけで多様性を認定しない。仮定と失敗の違いを見る |
| 相互作用 | 有用な指摘は生まれたが、全般的な最終品質へ届かなかった | 議論の量でなく、反例から変わった source とその実測を次の相談へ使う |
| 資源 | 協働の既知 output は約2倍。実験 CPU は全員で1つ | 人数追加はしない。計算容量を増やしたと仮定せず、費用不明も保持 |
| 測定 | usage gap で元 runner は正常終了した adaptive の封印・採点を止めた | 新版で品質・費用・上限・回収を分ける。旧結果を復活させない |
| 比較の設計 | solo 対 adaptive だけでは、次の指示改良の効果を分離できない | 同じ協働能力の旧指示対新版を主比較にし、strong solo の同条件基準も維持 |

## 今回実装したもの

- 保存済み公開 JSON を検査・集計する `public_frontier_v1/audit.py`。
  candidate を実行せず、入力/source の追跡性、目的別上限、単一候補の非劣集合、負荷帯・family を残す。
- 実験用の [failure_refinement_v1/adaptive.md](../experiments/development-harness/scheduling/failure_refinement_v1/adaptive.md)。
  現在の失敗から相談を選び、別案に共通する前提を反例・試作で変える。
  初期の独立探索も許し、固定人数・固定交換数・新しい記録様式は要求しない。

これは H4 の介入候補であり、効果は未検証。プロジェクトへ配布済みの改善とは言わない。
指示が長くなる分、形式的な報告や局所改善へ偏る可能性も比較で検査する。

## 次の実行順と完了条件

1. 正常終了した提出物を usage 検査前に封印する新版の回収経路を作り、
   usage 欠落・期限・費用超過でも品質/費用/上限/cleanup を取り違えない疑似provider検証を行う。
   これは次の比較の必要条件。汎用 collector や追加の会話管理基盤へ広げない。
   **追記: actor単位の実装・校正は完了。** [native_recovery_v1](../experiments/development-harness/scheduling/native_recovery_v1/README.md)の
   source一致7試験が通過し、使用した19 containerを全て削除した。新しいlive開始はなく、次は2へ進む。
2. 旧協働指示・新版・strong solo の新しい有限 protocol を固定する。
   条件間の課題・公開能力・model/effort・時間・CPU/memory を揃え、全開始と欠測の扱いを先に決める。
   既に使った課題を未使用 confirmation と呼ばず、source 一致 preflight 後に開始する。
3. 実際の選択済み成果で到達力と退行を評価する。共通失敗を変える候補が生まれたかは機序の診断、
   最終品質が上がったかは主判定として分ける。費用が欠ければ効率・上限適合は保留する。
4. 改善がなければその版は未達として閉じる。新しい証拠なしに本数・人数・話題を増やさない。
   改善が見えても未使用条件で確認するまで通常配布と安定した能力拡張の認定は分ける。

この順序は今回の planning prior、owner は primary/integrator。
公開記録の誤り、別の完全な候補記録、課題の改善余地を否定する証拠が出れば見直す。
現在までの実行数や文書量を主目的の達成として数えない。

## 同日、実比較を完了してからの再レビュー

全3条件が正常終了し、全提出物を封印して72採点を完了した。
改善版は標準比で価値+175・最重要+7・未完了価値−1920。一方、中負荷の最重要が1件減り、
事前の採用候補条件を満たさなかった。単独比も価値−185・最重要−7で、通常配布は保留する。
回収修正によって品質を測れたことは前進だが、単独の到達水準を越える目的は未達である。

| 批判する対象 | 実比較からの判断 |
| --- | --- |
| 指示が具体的なら品質も改善するという期待 | 反例からsourceが変わり合計品質も増えたが、退行が残った。手順の実行を成功へ読み替えない |
| 未完了を減らせば十分という解釈 | 改善版は標準の未完了価値を1920減らしたが、単独より81多い。重要classとの両立も未達 |
| もう一度選択だけを直す案 | 最終2協働成果物の事後の目的別・ケース別上限も11761/563で、単独11822/567以下。全開発候補の上限ではないが、既存2提出物の切替では不足 |
| 毎回白紙から開発する実験設計 | 全条件が基礎dispatch・予約・harnessを作り直している。既に強い成果から継続する問いも必要 |
| 強い成果を渡して協働だけ追加開発する案 | 不公平な対照になる。同じ初期sourceと追加開発を持つ新しいstrong soloを置く |
| 成果が出るまで題材や人数を変える案 | 現版を閉じ、次の問い・全予算・採否を別に固定する。旧得点と開始枠を維持する |

次は[同じ強い成果からの継続開発](../experiments/development-harness/scheduling/refinement_cohort_v1/continuation-design.md)を具体化する。
現成果へのanchoring、単独のさらなる改善、課題の残余が協働に適するかも反証対象に残す。
これは今回の指示版の成功認定でも再試行でもない。新しい接続とprovider-free校正・有限protocolが次の作業であり、
追加liveはまだ登録していない。一般推奨へ反映する前に、最終成果で単独を超えることを確認する。

## 継続開発の期限停止からの修正

その後、共通初期sourceの接続を校正して実比較を開始したが、単独のターンが40分以内に終わらず停止した。
sourceと公開検証は保存されている一方、原契約は正常終了を要求するため、協働開始も採点も止めた。
この原判定を維持し、約0.06秒を丸めて成功にする扱いや、協働側だけを後から始める扱いはしない。

見直すのは停止の数値より、何を評価できるとするかの契約である。
予算終了時の成果物品質を知りたい場合、予定した期限停止は観測対象の終わり方になり得る。
通常終了、指定成果物の回収、品質、全費用、時刻の上界を分ける必要がある。
ただし停止・回収に時間差があるので、回収後の成果を「締切ちょうどの品質」とは呼ばない。

[別契約の実装・4試験](../experiments/development-harness/scheduling/deadline_capture_v1/README.md)では、
元のwithholdを保持して期限停止後の有効な提出を採点し、不正はinvalid-policy、未提出と外側中断は保留した。
書込み中の子を停止した後のsource不変も確認した。
実Dockerの不正提出試験で、旧adapterの終了コード想定が固定評価器と合っていない問題も見つけ、新版だけで修正した。
次はこの契約を両条件の有限比較へ接続する。原runの再採点や追加実モデルで今回を成功に変えてはいない。
