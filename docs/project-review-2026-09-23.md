# 2026-09-23: 成果へ近づくための実験の再設計

ユーザーの「今の実験はイケていない。目的を最短で達成する進め方を再検討してほしい」という依頼への判断。
実験の負の結果を消さず、次に投資する対象を変える。[主計画](project-plan.md)へ反映した。

## 何が問題だったか

| 観察した事実 | そこから判断できること | 判断できないこと |
| --- | --- | --- |
| [3条件比較](../experiments/development-harness/scheduling/refinement_cohort_v1/result.md)で協働の改良版も単独以下。保存済み最終協働候補の事後上限も単独以下 | 選択だけの改善では、この候補集合の不足を埋められない | 新しい候補・統合・別課題の協働も無効とは言えない |
| 3条件とも基礎dispatch・予約・実験harnessを作成し、同系統の解へ到達 | 開発時間の使い方と初期実装の共有は診断に値する | 同系統というだけでは、集団的バイアスや同一実装を証明しない |
| severeには資源容量上、全完了できない場合がある。現在の参照を単独が上回る | 満点との差が、そのまま協働で回復できる余地ではない | soloが世界最適・課題が飽和したとは言えない |
| 継続比較が期限停止し、capture・Docker回収・起動時計の別版を追加した | 品質測定を止める基盤不良は実在した。修正には価値がある | 修正の完了は、協働の品質改善ではない |
| 独立評価の24例は、一つの開発成果を24入力へ適用したもの | 頑健性の診断はできる | 24回の独立した開発比較や、別分野への再現性にはならない |
| 協働usageがpartialでも成果物品質は回収できた | 品質と使用量の分離は今後も再利用できる | 同じtoken予算、請求完全性、費用効率は認定できない |

問題は「協働が負けたから題材が悪い」ことではない。
**課題・時計・回収を次々に整備することが主工程になり、どの開発上の不足を直すと
利用者の成果が上がるかを短く試す経路が弱かった。**
次の接続が実装しやすいことと、次の問いに答える価値が高いことを混同していた。

## 比較した進め方

| 案 | 利点 | 現在の費用・弱点 | 今回の採否 |
| --- | --- | --- | --- |
| 新時計でschedulingの継続pair | 既存資産が多く、直前の未測定を減らせる | 同じ系列での最適化差。到達可能な余地と開発一般への意味が未確定 | 主工程から保留。将来の最適化用補助課題として保持 |
| soccerへ切替 | 戦術・推定・制御の異なる案を試せる | [入口監査](agents/soccer-candidate-entry-audit-2026-09-08.md)でseed所有・隔離・再現性に不足 | 今は選ばない。新しい採点器作りへ戻る費用が大きい |
| このrepoの小さな保守課題 | 利用価値と既存checkが明確 | 強い単独も満点になる過去の不足を繰り返しやすい | 更新の回帰に使う。能力拡張の主実験にはしない |
| 既存の難しい実リポジトリ課題 | 要求・codebase・参照・評価imageを借りられる。探索・互換性・統合を直接扱う | 公開課題への学習混入、oracleの過剰制約、最新modelでは容易な可能性 | 第一候補。少数の入口校正とstrong soloで反証する |
| 新しい開発studio/汎用実験基盤 | 自由度が高い | 成果を測る前の製品開発が増える | 不採用 |

この順位はplanning prior。ownerはprimary/integrator。
外部課題の接続や評価が想定以上に重い、妥当な別解を拒否する、現modelで容易なら更新する。
「OSSだから難しい」「benchmarkの名称にhardがあるから適格」とは扱わない。

## 外部資産を選ぶ理由と限界

2026-09-23に、[SWE-Bench Pro V2の公開tree](https://github.com/scaleapi/SWE-bench_Pro-os/tree/66f92766bba642462d4bbe5479e83f91f9211862/v2)を読んだ。
課題ごとのcontainer image、提出diffを別環境で採点する経路、referenceと空patchの境界検証が公開されている。
これは、このプロジェクトが繰り返し実装していた工程を省ける可能性がある。
上流の成功報告はローカル校正の代わりにせず、image・sourceを固定して最初の一件で確かめる。

HARD-51は旧model群の失敗から作られた層であり、Astra/Sol/Opus 5.5/Grok 4.7の未達証明ではない。
公開課題なので学習への混入も否定できない。今回の用途は限定した開発手順の探索。
一般化の確認には、介入選択に使っていない別repo・別要求が必要になる。

[SWE Atlas](https://github.com/scaleapi/SWE-Atlas)も候補に挙げた。
広いrefactoringは目的に近いが、rubric評価をそのまま客観的な動作判定へ置き換えず、
まず実行結果で要求充足を検査できる課題を優先する。両suiteのadapterを同時に作らない。

## 何を比較すれば改善へつながるか

まず、現在の強い単独が残した具体的な不足を得る。
基盤タイムアウト・矛盾した要求・正解の隠蔽を、知的な未達に含めない。
選んだsourceと公開情報を双方へ同一に渡して、単独の追加開発と協働の追加開発を比較する。
単独の過去得点を固定対照にせず、追加の時間でも改善する機会を与える。

介入は観測した失敗に合わせる。
影響範囲の見落としなら独立した呼出し元探索、誤仮説なら再現と反証、
実装候補の不足なら別の前提での試作、統合の失敗なら結合動作の検査を選ぶ。
role名、人数、会話量を固定の正解にしない。
実験中のagent起動はprotocolとそのsessionの権限に従う。この再検討作業ではsubagentを使っていない。

主判定は、変更を含む最終成果物の公開要求充足と既存機能の退行。
途中の候補が良くても提出に統合されなければ未達とする。
「何が変わったか」の診断には、公開の反例、source差分、実行結果だけを使う。
内心・説得力・自称の独立性を採点しない。

## 新しいmodelをどう使うか

- 通常開発のSol、別視点候補のGrok/Claudeを利用できる基盤へ更新する。
- 現在のstrong solo基準のAstraを、新しい名前というだけでSolへ置き換えない。
- providerが異なれば、知識・CLI・effort・価格も変わる。異種model協働の改善は、まず構成全体の改善として測る。
- advisor側modelが単独でも十分なら、routingの方が単純で安い可能性がある。
  その判別が採用判断を左右するときだけ、開始前に予約したmodel単独の診断枠を使う。
- 同一model協働の効果、異種modelの補完、単なる追加計算は別の問い。初回から全要因を総当たりしない。
