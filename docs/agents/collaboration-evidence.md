# 協働の実測と適用範囲

更新: 2026-09-09。方式の選択時に[協働モデル](collaboration-model.md)と一緒に参照する。
使い方の説明、実行できた証拠、成果への効果を区別し、未測定を改善率で埋めない。

別projectへは[配布用の実測snapshot](../../project/docs/agents/collaboration-study-evidence.md)と
同梱の原集計を提供する。通常のorchestration skill/playbookから参照でき、基盤repositoryのcheckoutを必要としない。
この導線の利用確認は、案内による開発性能改善の実測とは分ける。

## この実測集合からまだ言えないこと

queueと保存候補分類では単独も満点であり、強いsoloの探索・判断が行き詰まる難題での
協働の到達力を測った集合ではない。追加費用の観測は保持するが、難題での相談・案収集・競合実装を
控える一般的根拠にはしない。主評価の選定は[改訂計画](../project-plan.md)に従う。
負の結果を記録できたことと、単独の到達水準を越えるという目的の達成は区別する。

## 動的schedulingのadaptive探索

[2026-09-09の1組](../../experiments/development-harness/scheduling/adaptive_pair_v1/result.md)では、
gpt-6-astra/highの強いsoloと、途中相談・独立実装・検証・選択を許すadaptiveを各40分上限で実行した。
両developerは正常終了したが、通知隣接の使用量不足で**元比較はwithhold**。
選択済み成果物だけの別診断で、期限内価値は単独11464/協働11422、最重要完了は564/550だった。
重い資源希少条件では協働成果物の価値+110・最重要+3だが、突発負荷などで退行した。
この局所差や1組の結果を一般的な協働改善率へ移さない。

協働は4参加者で、独立候補、反例修正、候補sourceの固定、性能修正の同値検査を生んだが、
最終選択された品質の全般的改善は確認できなかった。単独も複数方式・46設定・自作検証を実施した。
既知のoutputだけでも協働97664/単独49534。協働の全費用とtoken上限適合は不明であり、費用効率を認定しない。
保存済み公開実験の[別診断](../../experiments/development-harness/scheduling/public_frontier_v1/result.md)では、
協働の全24例が揃う13記録をケースごと・目的ごとに最良選択しても上限11521/565で、単独11607/581以下。
developer記録の算術上限であり独立採点ではないが、この集合では選択だけを直しても不足する。
次の品質仮説を、共通する失敗の反証から候補の改良・新しい統合へつなぐ[実験用指示](../../experiments/development-harness/scheduling/failure_refinement_v1/README.md)へ変えた。
品質・費用・cleanupの分離は比較の前提として修正する。新しい指示の効果は未検証。
追加runで勝敗を探さず、旧protocol・原結果は変更しない。配布snapshotへはまだ転記していない。

## 保存候補の受入点検への事前助言

[固定relayでの1組](../../experiments/development-harness/selection/relay_v1/result.md)では、
単独と「コード・仕様を読むadvisor→公開検証できるmaker」がともに4分類一致・採用保留だった。
単独132.980秒、相談あり195.559秒。相談側は時間47.06%、input38.17%、output38.51%増。
この範囲で固定事前相談を既定に追加する根拠はない。追加runで勝敗を探さない。

2候補とも既知の境界欠陥があり、分類は旧2群の保存判定との一致。自由文の真偽・全品質はunknown。
4分類は独立4課題ではない。途中での相談選択・複数実装・一般的な選択能力は測定対象外。
単独にも検証能力を与え、助言側の全消費を含める対照を維持する。
この記録は基盤側の新規観測であり、既存の配布snapshotを更新したとは扱わない。

## 事前相談による証拠統合

対象はF12-L revision 3の、公開された数値・根拠ID・移行制約を最終記録へ統合する限定課題。
gpt-6-astra/highを要求したCodex実行で、soloと「事故・隔離・移行を先に点検するadvisor→fresh maker」を一組比較した。
[protocol・結果・出典](../../experiments/development-harness/consultation/synthesis-result.md)。

| 観測 | 現在の判断 |
| --- | --- |
| 元の固定得点は両方10/12だが、否定表現と関連unknownの重複に対する誤判定を校正で再現 | 品質改善の判断は保留。得点を上書きせず、品質付き速度比を出さない |
| 相談側の提出までの時間19.3%増、input44.8%増、output6.5%増 | この条件で常時事前相談を既定化する根拠はない |
| 独立した助言の受渡しと全参加者の停止・消費回収は成立 | 運用経路の証拠。助言の有用性や他の協働方式の効果とは分ける |

AIがこの観測を使う際は、課題、公開tool、model要求、直列の関係、全体予算、評価の限界を添える。
他の課題、途中の相談、独立review、複数案・複数実装、並列分業へ数値を移し替えない。
同じ公開検査で自己検証できる場合に、事前相談を自動追加する一般規則は作らない。
相談するなら、追加の観点・証拠がどの判断を変えるかを具体化し、全費用を見て採否を決める。

次の仮説は、公開情報を一通り点検した後の具体的な不足に対する相談が、常時事前相談より
無駄を減らせるか。まだ比較していないので推奨や改善率は付けない。
現在のdatumはduration atlasへ混ぜず、独立したpilot記録として保持する。

## 評価器に戻す学習

known-goodと悪い成果を区別できるだけでは、協働比較の準備完了ではない。
正しい否定表現、関連する複数の根拠、妥当な別表現も受理できる必要がある。
この校正が失敗したら、改善率の集計を止めて版を分けて修理する。人やLLMの採点で埋め合わせない。
新しい評価版と確認課題での再比較が終わるまで、一般的な品質改善を主張しない。

[synthesis scope v2](../../experiments/development-harness/consultation/synthesis_v2/README.md)で、
scopeとtopicを公開された構造で判定する評価を実装・校正した。正当な10候補の受理と、
構造化された過剰一般化・根拠欠落など27候補の拒否を確認したが、自由文の虚偽と無効な
運用手順の2候補は通る。この限界を含めて校正結果とし、旧pilotの品質保留は解除しない。
AIへ返す学習は「検査できる性質を明示し、未測定の品質を得点から推測しない」。
この評価器の修理は、相談そのものによる品質・速度の改善を示す実測ではない。

F04-Lでも[動作監査](../../experiments/development-harness/selection/f04-lifecycle-audit.md)により、
直接上書きと空白引数を壊すwrapperが旧評価4/4を通ると確認した。別の動作probeでは検出し、
異なる原子的writerも受理できた。過去10観測中9満点は旧検査の到達率であり、成果物未保存のため
今回の欠陥があったかは不明。再採点や協働効果の推定には使わない。

## 独立reviewから修正する場合

[queue review別版の実比較](../../experiments/development-harness/queue_review/v1/result.md)では、
同じ初期実装をsoloで点検・修正する条件と、独立review→fresh makerを比較した。
公開checkは両方が利用でき、最終品質は評価側が実fileとCLIの動作から判定した。

| 初期条件 | 観測 | 採否 |
| --- | --- | --- |
| 直接上書き＋引数再分割の欠陥 | 両方式4/4。review側の時間84.2%増、input86.7%増、output81.8%増 | この課題で常時reviewを追加する根拠にはならない |
| 正しい実装 | 両方式4/4・変更なし。review側の時間189.3%増、input152.6%増、output205.5%増 | 退行は観測しなかったが、追加費用が生じた |

全6participantの停止・usage・外部採点を確認。各初期条件1組の探索で、モデル要求はgpt-6-astra/high。
これをreview一般、複雑な実案件、途中相談、複数実装比較へ広げない。
正常終了する別process実行、書込み途中の中断、電源断、並行writerは異なる検査対象として扱う。
今回の合格は後ろ3つの保証を含まない。

ハーネスへ戻す判断は、この条件で常時reviewを既定化しないこと。
次の仮説は、まず公開checkと自力修正を進め、なお残る具体的な不足を相談理由として渡す方式。
起動判断と自己検査も全費用へ含め、同じ協働能力を持つ改良前後を比較する。
この仮説を基に、以下の情報介入を一組比較した。一般推奨へは昇格させない。

## 同じ相談能力へ判断材料を追加した場合

[条件付き相談の初回比較](../../experiments/development-harness/queue_review/conditional_v1/result.md)では、
両側に自力調査後のsubmit/consultを許し、一方だけに前回の2組の範囲付き観測と起動案内を追加した。
両側とも相談せず4/4へ到達した。情報ありは85.520秒、対照は95.209秒で、input13.615%減/output9.648%減。

事前の候補条件は満たしたが、時間基準の内側に約0.168秒入っただけの1組である。
判定は「独立確認候補」とし、一般既定にはしない。両側の相談選択が同じなので、
この差から相談起動の改善や、相談を省いた効果を推定しない。順序/cache/モデルの変動も残る。
今回未発動の相談経路の実モデル効果、意味上の相談必要性・案内採用はunknown。

AIへ渡すのは、この条件・観測・限界と次の確認点を伴う情報。
「情報を足せば10%速くなる」「相談を減らせば良い」という一般規則にはしない。
留保していたconfirmationは使用済み。次の確認は、新protocolで順序と本数を固定し、
同じ入力なら反復と明示して、差なし・逆転・欠測も保存する。
