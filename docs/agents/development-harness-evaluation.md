# 開発ハーネスの規模別評価

更新: 2026-09-07。時計・停止・費用の原則を維持し、主課題の採用は難題の適格性に従う。
[現行計画](../project-plan.md)を実行順の正本、[協働実験計画](collaboration-experiment-plan.md)を
今後の比較設計とする。[Cycle 005までの再計画](development-harness-next-plan.md)と
[以前の方針](development-harness-evaluation-through-cycle-004.md)は履歴。
旧protocol、clock、得点、raw artifactは変更しない。以下の新版ルールを既存runへ遡及しない。

## 主課題は規模ではなく、単独の到達困難さから選ぶ

以下の小規模・大規模の区分は実行と観測の分類であり、主課題の採用条件ではない。
主評価では[難題の適格性ゲート](collaboration-experiment-plan.md)を使い、強いsoloの探索・反証・選択・統合に
残る不足を、協働で越えられるか測る。単独が容易に満点になる課題は回帰・低難度対照に位置づける。
主指標は最終成果の到達・未達と品質であり、到達水準が揃った場合の速度と全費用を併記する。
難度校正で単独未達の課題層を選ぶことは許容し、協働結果に基づく事後選別や確認側のsolo成功例の除外はしない。

## 規模の定義

| 観点 | 小規模 | 大規模側の結合した変更 |
| --- | --- | --- |
| 利用目的 | 一つの局所修正・改善 | 一つの実利用経路を継続して成立させる変更系列 |
| 結合 | 局所の契約・回帰が中心 | component間の契約、永続状態、実行と停止、既存データ・配布の整合 |
| 継続性 | 一つの作業で完結 | 以前の実装・状態が後続要求の成否に影響する |
| 判定 | 仕様と関連回帰の外部検査 | 縦断利用、追加要求後の退行、旧状態・中断・配布経路の外部検査 |

分類はtaskの実需要・依存・変更履歴から開始前に決める。行数、file数、時間、agent数、
段階数を増やして規模を作らない。多数の既存テストを回した局所修正を大規模と呼ばない。
独立小問の寄せ集めや履歴表示の拡張だけでは、大規模側の代わりにしない。
同一projectの一つの変更系列も、そのproject全体や他分野への汎化を証明しない。

## 一つの比較単位

同じsource、task、公開要求、model指定、CLI、権限、予算・停止方針のA/Bを対応付ける。
変える介入を先に明示する。全段階と修正sessionを一つのcampaignとして集計し、
段階、checkpoint、テスト件数を独立sampleとして数えない。
強い対照に同じ検証手段と情報を与え、検証を禁止することで差を作らない。

大規模側の後続要求・公開条件・予算予約を先に固定する。前の実装が作った実データを引き継ぎ、
後から別の正解実装の状態へ交換しない。新sessionの規則を揃え、累積予算をリセットしない。
公開段階が異なる時点では共通要求の品質と全体進捗を別々に報告する。

task/source/環境をblockにして実行順を事前に割り付ける。隠されたoracleは開発者へ見せず、
終了後に同じ検査を行う。順序・seed・全cell・未着手を台帳に保存する。
初回の少数例は探索として扱い、確認の本数と精度目標は別protocolで決める。

## 観測の新版ルール

次の標準は正常提出、固定上限での停止、段階境界での回収。実行中の周期pauseを必要条件にしない。
sourceはwriter停止を実際に確認してから保全し、hash付きarchiveを独立環境で検査する。
動いているworkspaceの無停止copyを整合したsnapshotと仮定しない。

早期の正常提出物を変更しなければ、後の予算時点にも同じ成果を持ち越せる。
待機を作業時間に加算しない。打ち切り成果は提出と区別する。
停止要求から実停止までの書込みを否定できない場合、要求時刻ちょうどの品質はunknown。
両条件の実際の取得区間と停止遅延を併記し、事前固定した許容幅を超える同時間比較は行わない。
許容幅・capture能力の校正を行うまで、精密な固定時刻の品質を測れるとは主張しない。

途中の到達曲線が採否に必要な場合だけ、別の短い上限の独立runを事前登録する。
疎な観測から正確な初回合格秒を補間しない。追加runを成功するまで繰り返さない。

## 速度・品質・費用

| 指標 | 定義と禁止する読み替え |
| --- | --- |
| 品質付き提出時間 | 正常な提出eventまでのelapsed time。固定品質を満たす場合にだけ速度として扱う。container停止時間は別記録 |
| 到達率・未完了 | 全開始cellを含める。未達や中断を上限秒の完成とせず、成功例の平均だけで選ばない |
| 固定予算方針での品質 | 公開済み要求ごとの合格・不合格・未確認。上限と実取得時刻の差を隠さない |
| 変更への対応 | 後続要求の達成、以前通った要求の退行、実データとの互換性、再開時の副作用 |
| 利用可能までの総時間 | 必要な準備開始から共通の最終検証・配布確認までの実時間。並行作業を足して総時間にしない |
| usageと外部費用 | 完了sessionの各usage、欠測、準備・検証・統合費を分離。未知の単価で金額を計算しない |
| 補修の成果 | 後処理や統合修正は別artifact・費用。元のcandidateや採点を交換しない |

利用可能時刻は、その条件の元の成果が最終条件を満たした場合だけ確定する。
不合格を検査完了時刻の「完成」にせず、統合者の後の修正も元の比較時間へ戻さない。

介入で自動実行する公開test、feedback、修正、待機は開発予算へ含める。
最終の独立評価も総時間へ含め、チェックを外へ移しただけで速く見せない。
配布品質を比較するときは各条件の成果へ同じ必須検査を適用する。
品質の下位項目と時間・usageを別々に出し、単一の「効率点」へ合算しない。

## 品質の受入れ

公開要求と実行可能な検査を対応付け、正しい実装と代表的欠陥で開始前に校正する。
機能、保全・堅牢性、実際の利用、追加変更・互換性のうち適用する範囲を明記する。
要求ごとに部分達成を使うなら、その状態を開始前に具体化する。
データ損失や誤った成功確定などtaskの重大欠陥はhard guardとし、速度や他の成功で相殺しない。

人やLLMのレビュー点数を合否へ入れない。自動検査へ落とせない品質は未測定として残す。
通常のcode reviewや実用コードの統合判断は行えるが、その結果で元の自動得点を変更しない。
後から見つかった欠陥は新版の校正に反映し、旧得点と別の観測として保存する。

検査件数、command回数、diff量、設計用語、modelの完成宣言は品質の代理にしない。
必須集合の欠落・重複、source変化、評価器異常、欠測を合格に変えない。
同じ満点が続く場合、実際に差がない可能性と評価範囲の狭さを区別する。
望む条件が勝つまでtaskを難しくすることも、同じ小課題を増やすこともしない。

## 停止・採否・現在の状態

停止証拠なしで外部評価を開始せず、状態不明のまま次の開発を起動しない。
未知usageをゼロにせず、予約された時間を実測時間に表示しない。
中断後の保全成果は品質だけを観測し、提出・予算内完了へ昇格させない。
基盤の重大故障では未開始の比較を止め、すべての状態を報告する。
条件固有の資源負荷が故障へ寄与した可能性を、無関係な外乱として消さない。

効果は速度のみ、品質のみ、両方、trade-off、不明で報告する。
初回は候補選定まで。一般的な改善の採用には、別taskでの事前固定した確認と費用の評価が必要。
修正の局所再現・回帰・配布成功は、その修正の採用根拠にはできる。

現在あるものは、有限の段階runner、archive、独立observer、予算の開始判定、中断成果の後処理に加え、
新clock、周期pauseなしの終端回収、公開feedback方式。Cycle 005で使用済み。
今後は[協働実験計画](collaboration-experiment-plan.md)に従い、方式ごとの課題適格性、
複数参加者の受渡し・全停止・全費用、継続開発の評価を確認する。
全run数・phase/session上限・時間・usage・評価費・保存容量・停止許容幅を固定する前にliveを始めない。
ownerはprimary/integrator。ユーザーへ採点やlog保守を求めない。
