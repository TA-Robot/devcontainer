# 開発ハーネスの規模別評価

更新: 2026-09-05。状態: 小規模の実測はcycle-001にある。大規模01の課題・外部CLI検証・有限段階実行runnerを実装し、fake providerと実Dockerの事前検証を完了。大規模の比較結果はまだない。実行優先順位は[現行計画](../project-plan.md)を正本とする。

## 評価したいこと

このdevcontainerで、局所的な修正から継続的な機能開発まで、品質を保って完成へ進められるかを評価する。小規模と大規模は別々に結果を出す。小規模での高速化だけを全体の有効性の根拠にせず、大規模で得た仕組みが小さな仕事へ余計な負担を加えないかも確認する。

cycle-001は、明確な仕様を持つ単一の保守変更について、環境不備の除去を試した小規模の予備評価である。周辺121テストを実行したことや、primaryの調査・buildに時間がかかったことは、開発task自体を大規模にしない。従来atlasのS/M/Lはfamily内の相対分類であり、そのLをこの評価の大規模へ自動的に対応づけない。

## 規模の分け方

| 観点 | 小規模 | 大規模 |
| --- | --- | --- |
| 開発単位 | 一つのバグ修正、局所改善、小さな機能追加 | 一つの利用目的を満たす継続的な機能開発・移行 |
| 判断 | 要求と変更箇所が比較的明確 | 既存設計の理解、要件の具体化、分割、互換性の判断が必要 |
| 結合 | 局所の仕様・回帰が中心 | 複数componentの契約、永続状態、利用経路の整合が必要 |
| 継続性 | 一つの作業単位で完結 | 前の成果を保持しながら後続要求・統合・再開へ進む |
| 完成判定 | 外部の意味的検証と関連回帰 | 利用シナリオ、段階ごとの検証、変更後の回帰、運用・移行確認 |
| 主な失敗 | 誤修正、見落とし、環境修復への浪費 | 設計の行き詰まり、要求忘れ、後戻り、統合不良、復旧不能 |

規模は事前に要求・依存関係・状態・完成条件から分類する。コード行数、変更file数、実行時間、agent数を合格条件にしない。早く正しく完成した成果を減点したり、遅い失敗を大規模と呼んだりしない。一度に解ける独立な小問を束ねただけの課題は、大規模の代替にしない。

## 比較方法

小規模では、同じ出発点・task・model・effort・CLI・権限・上限の対照／改良条件を比較する。大規模では、同じプロジェクトを発展させる一連の開発を比較単位とする。途中の段階は独立sampleとして水増ししない。

大規模の流れは、要求の具体化と設計、動く縦断機能、通常利用の完成、事前に定めた追加要求への対応、再開・統合・運用確認とする。追加要求の内容・投入条件・評価を比較前に固定する。例えば「最初の機能提出後に既存利用者の設定を維持した更新へ対応する」であり、対照の失敗を見てから改良側に有利な要求へ変えない。

固定の累積予算時点と成果提出時点で、変更済みのsource・未commit差分・必要な状態・task履歴を外側で保存する。snapshotの評価は別の一時環境で行い、candidateの作業状態を変更しない。追加要求前の機能が後で壊れていないか再評価する。評価結果をcandidateへ返すか、評価中の計時を止めるかも両条件で同じにする。

自然なcontext圧縮・再開は記録する。計画的なsession切断を入れる場合は、両条件へ同じ段階で適用し、引継ぎに使えるartifactと履歴の規則を固定する。新sessionから始める方式と継続sessionの方式を無言で混ぜない。再開後も時間・usage・失敗履歴を累積し、予算をリセットしない。

taskの選定や介入を考える探索用runと、固定した条件で測る比較runを区別する。同一taskへの適応で得た差は探索結果と明記し、別taskでも再検証する。反復するときは実行順を交替し、各条件を元の出発点へ戻す。失敗・中断・未完了も母数と報告に残す。

## 評価する指標

| 指標 | 記録・判定 |
| --- | --- |
| 完成品質 | 外側で実行した利用シナリオ、意味的検証、既存回帰の結果。必須要件は個別に合否を示す |
| 時間内の品質 | 事前に決めた累積予算時点で、何が動き、何が未実装・不合格か。後の完成結果を過去へ補わない |
| 完成までの時間 | 外部の完成条件を初めて満たすまで。未完了は上限到達として扱い、速い失敗を高速完成へ数えない |
| 変更への対応 | 追加要求の達成、既存機能の維持、以前合格した要件の再失敗と復旧 |
| 再開・統合 | context切替・中断後の継続、契約の整合、運用シナリオでの成立 |
| 消費 | 全sessionの入力／cache／出力usage、環境起動・build・test時間。観測できない値はunknown |
| 人間の負担 | 実際の介入回数と理由、review・修正・統合に要した時間。diff量やモデルの自己申告で代用しない |
| 改良の総費用 | ハーネスの調査・実装・検証費用と、各開発runの費用を分けて記録。作成費用を除いたrun時間だけでROIを主張しない |

品質の必須条件と、改善案の採否は分ける。同じ必須品質へ達したrun同士では時間を比較できる。到達品質が違う場合は品質と費用を併記する。小規模と大規模の時間短縮率を一つの平均へ潰さない。check数、commit数、agent数を成果点にしない。

## 上限と判断の所有権

以下は今回の選定用の仮置きであり、runnerの実装済みdefaultでも、長く動かす最低時間でもない。ownerはprimary/integrator。pilotの完遂状況・usage・課題の構造に基づいて比較開始前に更新し、その理由を残す。

| 設定 | 分類 | 範囲・根拠・見直し条件 |
| --- | --- | --- |
| 小規模は30分／条件まで | cost capの候補 | cycle-001の数分という観測を踏まえ、少し広い保守にも余裕を持たせる。pilotで不足すればtaskと上限を再検討 |
| 大規模は累積1・2・4・8時間で観測 | planning prior | 完成だけでなく発展・手戻りを観測するための時点候補。task校正と資源見積りで選び直す |
| 大規模は累積8時間／条件まで | cost capの候補 | 無期限実行を防ぐ初期案。未完了なら部分品質として報告し、延長は新しい実験条件として扱う |
| 各規模でまず対照／改良の1組 | 探索用cost cap | 手順の成立と問題発見が目的。大規模1件の成功も、一般的な有効性の証明にはしない |
| 品質・変更保全・記録の独立性 | hard guard | taskごとの外部受入条件を満たす。計時短縮のために弱めない |

実行前には選択した時点・上限に加え、実行本数、session数の上限、usageまたは金額の停止条件、同時実行、評価費用の扱い、停止後のartifact回収を具体値で固定する。金額は実際の料金とusageを確認できた場合だけ算出する。これらが未設定の段階では長時間batchを起動しない。

## 次の実行対象と順序

まずこの基盤自身の実開発を候補にする。別プロジェクトが指定された場合は、その実需要と出発点に置き換える。課題候補は[選定メモ](../../experiments/development-harness/multi-scale/task-selection.md)へ置く。

1. 大規模候補の利用価値、現在の不足、実装境界、段階的な要求、外部受入シナリオを具体化する。単に評価を難しくする追加機能は入れない。
2. provider-freeの受入検証を校正する。欠けた実装を合格させず、複数の妥当な実装方式を許す。完成した解答をcandidateの出発点へ混ぜない。
3. 大規模の有限実行・snapshot・累積計測・停止／再開を検証する。fake processで上限とartifact保持を確認してからliveへ進む。
4. 大規模の現状評価を先に行い、詰まった箇所から介入を決める。その後に固定条件で再評価する。途中の変更は探索として記録する。
5. 同じ介入を別の小規模taskでも確認し、小規模側の品質低下・固定費増加を調べる。両規模の結果と残件が揃って次の採否を決める。

## 現在あるもの・必要な追加

cycle-001の[外部評価と測定script](../../experiments/development-harness/cycle-001/)は小規模の再現資産として保持する。そこに固定された900秒・単発session・特定taskの33checkを、大規模へそのまま流用しない。過去のsource hashとraw観測も変更しない。

既存の`scripts/benchmark-devcontainer.py`はcontainerの準備・停止・再開に利用できるが、開発campaignのcheckpointや累積予算を管理する機能ではない。追加する実行機能は、選定taskに必要な段階投入、外側のsnapshot、累積計測、有限停止／再開に限定する。汎用schedulerや別の開発製品を先に作らない。

その範囲の段階実行を`experiments/development-harness/campaign.py`へ実装した。[操作手順と検証](../../experiments/development-harness/multi-scale/README.md)を参照。大規模01では、初期導入、独自編集と更新・移行、中断復旧と配布の順に同じ機能を発展させる。35の外部シナリオと18のprovider-free事前テストを用意したが、これらの件数を大規模な開発成果の証明にはしない。

大規模評価とmulti-agent比較は別の軸。最初の比較では協働条件を固定し、複数agentが必要かどうかを規模の定義にしない。未許可のdelegationを自動的に有効にしない。
