# 開発ハーネス改善サイクル 002（進行中）

小規模修正だけで環境の有効性を判断しないため、同じ機能を3段階で
発展させる評価と、新しい局所修正の評価を組み合わせる。
現時点では大規模側の対照条件を完了した。改良条件、小規模の比較、
最終統合は未完了であり、改善効果や採用はまだ判断しない。

条件・上限・停止規則は[固定したプロトコル](../../experiments/development-harness/multi-scale/large-01/protocol.md)、
規模の定義は[規模別評価方針](development-harness-evaluation.md)を参照。

## 大規模側の対照条件

実需要のある project template の導入・継続更新・復旧を、一つの
実装として開発した。各段階は新しいセッションから既存コードと
引継ぎ文書を読み、公開済み要求を保持して進める。将来の要求や
外部テストの結果は開発セッションへ返していない。

| 段階 | 開発実行時間 | 外部シナリオ | 観測 output tokens |
| --- | ---: | ---: | ---: |
| 導入・保守的な更新 | 824.180 秒 | 22/22 | 23,969 |
| ローカル編集の保持・既存設定の採用 | 648.188 秒 | 28/28 | 18,982 |
| 中断復旧・取り消し・配布 | 1,081.340 秒 | 35/35 | 28,243 |
| 合計 | 2,553.708 秒（約42分34秒） | 最終35/35 | 71,194 |

各段階は独立標本ではない。シナリオは累積して再検証しており、
22+28+35を独立な成功例数として足さない。outputにはproviderの
reasoning outputを含むため、さらに加算しない。外部検証・環境構築・
primaryのレビュー時間は上表の開発実行時間に含まない。

累積1,800秒を目標に採取したsnapshotの実際の取得トリガーは
1,810.270秒だった。この途中成果も35/35を満たした。ただし、
基本シナリオの通過だけでは配布・互換性・レビューまでの完了を
意味しない。スナップショット時刻を正確な30分へ丸めて扱わない。

最終成果を使い、各前段階の実際のCLIが作成した所有情報を
更新・取り消し・再更新する追加検証も成功した。旧形式が保存して
いなかった過去のファイル内容を復元できるという意味ではない。

開発側は82テストと通常Docker buildの成功を報告した。
実行記録でもbuildの終了コード0を確認できた。一方、固定依存buildは
npmの名前解決、完成イメージの起動確認はDockerソケット権限で停止した。
後から外側の検証環境で、開発側が作った同じ完成イメージを使用し、
checkoutをmountしない導入・更新・復旧とミラの起動hookを確認した。
これは開発セッション内で必須確認を完遂したことには数えない。

## 改良候補と残る検証

既に必須確認で使っているDev Container CLIをimageへ同梱し、
暗黙のnpm取得をなくす。また、同じ呼出環境でDockerの前提を
確認し、実行不能なら取得前に理由を返す。いずれも現在は実imageで
検証中の候補で、権限変更やoffline buildを実現するものではない。

改良側は元の固定sourceに採用する環境変更だけを加え、対照側の
完成実装を持ち込まず同じ3段階を実行する。その後、同じ介入を
[新しい小規模task](../../experiments/development-harness/multi-scale/small-01.md)
でも評価する。小規模taskの開始前probeは16/21で、修正前の不具合を
再現できているが、開発比較はまだ実施していない。

## 解釈の限界

この課題は永続状態、後続要求、互換性、復旧、配布を結合させた
継続開発のpilotである。実行が約43分で終わったことを根拠に
減点することはしないが、週単位の大規模projectや複数teamでの
有効性まで確認したとも扱わない。1課題1組の探索的な比較であり、
一般的な速度向上の主張には別課題・反復・実行順の交替が必要になる。

証跡の正本はworkspace外のcycle-002専用state、停止時snapshot、
外部評価JSONに保存する。raw provider記録や認証情報は公開しない。
