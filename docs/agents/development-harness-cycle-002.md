# 開発ハーネス改善サイクル 002（完了）

小規模修正だけで環境の有効性を判断しないため、同じ機能を3段階で
発展させる評価と、新しい局所修正の評価を組み合わせる。
大規模側は両条件の3段階と外側の検証を完了した。今回は開発時間の短縮を
観測していない。小規模も両条件を完了し、成果の統合と最終検証まで終了した。
[機械可読結果](../../experiments/development-harness/cycle-002/result.json)に条件・usage・hash・検証を保存する。

条件・上限・停止規則は[固定したプロトコル](../../experiments/development-harness/multi-scale/large-01/protocol.md)、
規模の定義は[規模別評価方針](development-harness-evaluation.md)を参照。

## 大規模側の対照条件

実需要のある project template の導入・継続更新・復旧を、一つの
実装として開発した。各段階は新しいセッションから既存コードと
引継ぎ文書を読み、公開済み要求を保持して進める。将来の要求や
外部テストの結果は開発セッションへ返していない。

| 段階 | 開発実行時間 | 外部シナリオ | 観測 output tokens |
| --- | ---: | ---: | ---: |
| 導入・保守的な更新 | 824.180 秒 | 22/22 | 23,969 |
| ローカル編集の保持・既存設定の採用 | 648.188 秒 | 28/28 | 18,982 |
| 中断復旧・取り消し・配布 | 1,081.340 秒 | 35/35 | 28,243 |
| 合計 | 2,553.708 秒（約42分34秒） | 最終35/35 | 71,194 |

各段階は独立標本ではない。シナリオは累積して再検証しており、
22+28+35を独立な成功例数として足さない。outputにはproviderの
reasoning outputを含むため、さらに加算しない。外部検証・環境構築・
primaryのレビュー時間は上表の開発実行時間に含まない。

累積1,800秒を目標に採取したsnapshotの実際の取得トリガーは
1,810.270秒だった。この途中成果も35/35を満たした。ただし、
基本シナリオの通過だけでは配布・互換性・レビューまでの完了を
意味しない。スナップショット時刻を正確な30分へ丸めて扱わない。

最終成果を使い、各前段階の実際のCLIが作成した所有情報を
更新・取り消し・再更新する追加検証も成功した。旧形式が保存して
いなかった過去のファイル内容を復元できるという意味ではない。

開発側は82テストと通常Docker buildの成功を報告した。
実行記録でもbuildの終了コード0を確認できた。一方、固定依存buildは
npmの名前解決、完成イメージの起動確認はDockerソケット権限で停止した。
後から外側の検証環境で、開発側が作った同じ完成イメージを使用し、
checkoutをmountしない導入・更新・復旧とミラの起動hookを確認した。
外側での追加確認では82/82の回帰テスト（295.183秒）と固定依存buildも成功し、
ソースのhashが変わっていないことを確認した。これらは開発セッション内で
必須確認を完遂したことには数えない。

## 環境変更と大規模側の比較

既に必須確認で使っているDev Container CLIをimageへ同梱し、
暗黙のnpm取得をなくす。また、同じ呼出環境でDockerの前提を
確認し、実行不能なら取得前に理由を返す。約1.23GBのAIツール所有者変更の
層もsourceのCOPYより前へ移し、編集ごとの再実行を避ける。
これらはcommit `09ef4e4`として通常・固定依存build、起動確認、必須checkを
検証済み。実際にsourceだけを変更した再buildでも重い層の再利用を確認した。
権限変更やoffline buildを実現するものではない。

改良側は元の固定sourceに環境変更だけを加え、対照側の
完成実装を持ち込まず同じ3段階を実行した。同じ介入を
[新しい小規模task](../../experiments/development-harness/multi-scale/small-01.md)
でも評価した。小規模taskの開始前probeは16/21で、修正前の不具合を再現した。

| 段階 | 対照（秒） | 改良（秒） | 両条件の固定シナリオ |
| --- | ---: | ---: | ---: |
| 初期導入・更新 | 824.180 | 846.518 | 22/22 |
| 既存編集の保持・採用 | 648.188 | 586.678 | 28/28 |
| 復旧・取り消し・配布 | 1,081.340 | 1,391.950 | 35/35 |
| 合計 | 2,553.708 | 2,825.146 | 最終35/35 |

この1組では改良側が271.438秒（約10.6%）長く、観測outputも
71,194から80,095 tokensへ増えた。高速化の証拠としては扱わない。
改良側の30分snapshotは1,800.156秒で取得され、同じ第3段階の
35シナリオを通過した。実際の前段階の状態からの更新・取り消し・再更新も成功した。
改良側の固定依存buildはDocker接続の事前確認で停止した。必要なCLIは
同梱されていても、開発セッションのDocker権限の制約は残る。
外側では92/92の回帰テスト、通常imageの起動確認、固定依存buildが成功した。
通常image内のCLIが提出ソースと一致すること、および検証前後のsource hashの
不変性も確認した。外側の検証時間は開発セッションの時間に加算していない。

提出後のレビューでは、固定28シナリオが捉えていなかった採用時の権限差を
再現した。sourceが0644、既存targetが0600で内容・実行ビットが同じ場合、
対照側の第2段階と最終版は登録でき、0600を保持する。改良側は最終版でも
通常permission全体の一致を要求して拒否する。公開要求は内容と実行ビットの
一致を条件としているため、全要求を満たした成果同士の速度比較とは言えない。
固定シナリオの35/35は変更せず、この追加レビューと区別して記録する。
この指摘は実行中の開発セッションへ返していない。

機能の取り込みには、公開条件を満たしている対照成果を土台に選んだ。
両成果で管理データがGitの変更一覧へ現れることも再現したため、新規管理
ディレクトリ内だけに除外設定を置いた。project自身の`.gitignore`や旧状態の
no-opは変更しない。追加レビューでsource/targetの重複判定がrootや先頭の
二重slashを見逃すことを再現し、計画作成の段階で拒否するよう修正した。
これらは実験終了後の統合修正であり、測定した環境介入の効果に数えない。

## 小規模側の比較

supervisorの孤立判定の閾値がNaN・無限大・浮動小数点overflowを
受け入れる不具合を、同じ初期sourceから修正した。cycle-001とは異なる
設定経路だが、数値検証という同系列の課題であり、課題多様性は限定的である。

| 指標 | 対照 | 改良 |
| --- | ---: | ---: |
| 開発実行時間 | 312.563秒 | 347.433秒 |
| 外部シナリオ | 21/21 | 21/21 |
| 観測output tokens | 5,576 | 5,710 |
| 外側の回帰テスト | 50/50 | 47/47 |

改良側は34.870秒（約11.2%）長かった。ここでも高速化は確認できない。
どちらも開発セッション内ではUnix socketの制約によって15テストが失敗し、
外側で同じ提出sourceを検証すると全件成功した。この区別を維持し、
開発エージェントが必須確認を完遂できたとは判定しない。

固定版Codexの`--version`は正しい版をstdoutへ返していたが、読み取り専用
環境でstderrへ出るPATH alias警告をdoctorが版として読んでいた。
実際のCLIで再現し、version確認だけstdoutを優先する修正を統合した。
stderrだけに版を返すCLIと非zero終了も4つの回帰テストで確認し、
実CLIを使う読み取り専用image確認を固定依存buildへ追加した。
小規模の修正は、既存の下限・不正文字列の診断を保ち、起動前の副作用まで
検証した対照成果を採用した。doctor修正は測定後の改善であり、速度効果は未測定。

## 採否と次の優先順位

- Dev Container CLI同梱、Dockerの事前確認、重い所有者変更のbuild cache再利用は、
  個別の再現・検証を根拠に採用する。今回の開発時間を短縮したとは主張しない。
- templateの導入・既存編集の保持・復旧・取り消しは、公開要求と追加レビューを
  満たす対照実装を統合する。実需要のある利用経路として保守する。
- 次は開発エージェントの実行環境から、必要なUnix socket・Docker検証まで
  完遂できる経路を優先する。外側の検証成功を内側の能力と取り違えない。
- 速度を一般化する前に、異なる種類の保守と複数componentの継続開発で、
  反復数・実行順・評価時点を事前に定める。良い結果が出るまで試行を足さない。

両条件ともmodel/effortはgpt-6-astra/high、CLIは0.153.0を指定した。
providerが返していない適用値はunknownのまま扱う。各規模1組、実行順は対照→改良、
大規模の観測を見て選んだ複合介入なので、個々の変更の因果効果は分離できない。
専用containerの実行は直列だがhostの完全な専有は保証していない。
費用の観測は開発セッションのtoken usageであり、未確認の価格による金額へ換算しない。
primaryの準備・レビュー・統合のtoken量と人間の確認時間は未集計なので、
開発全体の総費用削減も主張できない。

## 統合後の最終検証

実装・テストの固定commitは`f1815548553455329874e9534bc2922d6f5eac25`。
Git archiveから新しい外部directoryへ取り出し、以前からある未追跡実験を
buildや評価へ混入させず、検証前後のsource hash一致を確認した。
結果報告と計画の更新はこの実装commitの後に行っている。

- agentctlの54テスト、lifecycleとnative contractの88テスト、build事前確認の
  4テストが成功。最終版の外部シナリオは小規模21/21、継続開発35/35。
- 実際の旧2段階のCLIが作った状態から更新・取り消し・再更新が成功。
  追加レビューのpermission保持と管理データのGit除外も成功。
- lock、CLI同期、wrapper、shell構文、Python compile、native template validatorを確認。
- 通常・固定依存の両buildが成功。checkoutをmountしない導入・merge・中断復旧・
  rollback、ミラhookと観測の永続化も両imageで成功。
- 固定依存imageでCLIのnetworkなし版確認、読み取り専用Codex capability診断、
  checkout library選択、Docker-in-Docker起動とdoctorが成功。

通常imageは`sha256:059d0c4d4438eab004ef332642a570d1847cda986e3c2b09aee4681f7ae3619e`、
固定依存imageは`sha256:6d77b4bab77a27aafd05a859058c4c12519b4fec9d0d240202a4dcff9c80f14e`。

## 解釈の限界

この課題は永続状態、後続要求、互換性、復旧、配布を結合させた
継続開発のpilotである。実行が約43分で終わったことを根拠に
減点することはしないが、週単位の大規模projectや複数teamでの
有効性まで確認したとも扱わない。1課題1組の探索的な比較であり、
一般的な速度向上の主張には別課題・反復・実行順の交替が必要になる。

証跡の正本はworkspace外のcycle-002専用state、停止時snapshot、
外部評価JSONに保存する。raw provider記録や認証情報は公開しない。
