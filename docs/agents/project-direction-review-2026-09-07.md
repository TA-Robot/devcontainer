- 期待する作用: 目的・評価・実利用という異なる観点からのcoverageと、primaryの判断への独立批判。
- participant: `critique_strategy`、`critique_experiments`、`critique_product`。

  同じmodelと共通説明を使っており、primaryの説明によるanchoringまで排除したとは言えない。
- 作業境界: native advisory。read-onlyは依頼上の制約で、強制隔離ではない。
  編集・実験・追加agentは依頼せず、primaryも3者の回答が揃うまで対象文書を変更しなかった。
- 人数3は今回のユーザー指定。各観点を返した時点で終了し、一般的な推奨人数やround数にはしない。
- primaryの責任: 根拠の確認、異論の扱い、採否、文書への反映。usageと人間のreview費はここでは未測定。

## 採否と次の作業

**採用する判断:** queueの順序反転確認を当面の主作業から外す。
登録済みの「独立確認候補」は変更せず、過去の結果・protocolも保持する。
案内を近く既定化する具体的需要が生じた場合は、確認の優先度を改めて評価する。

**primaryの提案も修正する:** 目的や方式表を再び大きく書き直さない。
既存資産から次の未解決判断を一つ選び、評価と実利用への接続を進める。

次の作業は、Cycle 002/003のtemplate導入・更新・復旧を対象にした適格性監査。
成果物は、既存source・公開要求・評価の再利用箇所と不足を示す比較設計一件とする。
監査で確かめる項目は以下。

1. 仕様追加後の互換性・既存編集保持・復旧・統合を外部動作で判定でき、妥当な別実装を受理できるか。
2. 独立した複数実装と公開checkによる選択を、既存runnerの狭い追加で比較できるか。
   これを第一候補とする理由は、方式比較が未着手で、候補生成・選択失敗・最終成果を分けて観測できるため。
   分担・統合は、要求から独立作業境界を示せる場合の代替候補。両方式を一介入に束ねない。
3. 強いsoloにも自己検証・別案・逐次試作を許し、同時間での成果と全消費を区別できるか。
4. 結果を通常の配布入口へ渡す最小の変更箇所を特定し、成果が正・負・不明の各場合に案内の何を変えるか。

第一候補はplanning priorで、scopeは次の比較の選定、ownerはprimary/integrator。
評価の識別力不足、実要求との不一致、接続費過大なら採用を撤回し、その理由を残す。
今回の相談では方式・要求系列・予算のlive protocolは固定していない。

3者の提案には、既知課題で方式を測る案と、新しい要求系列で配布案内を測る案の違いがある。
既知課題は校正や探索に再利用できるが、未使用課題と呼ばない。
案内の改善効果を確認する段階では、方式探索で結果を見た要求から分離した系列を使う。
新しい要求の根拠は実際の開発上の必要性とし、soloが失敗するまで難化しない。

次のmilestoneは、未測定の一方式について、最終成果と全費用から範囲付きの採否を一件増やし、
通常のproject入口でagentが参照できる状態へ戻すこと。
協働の勝利・発動数は完了条件にしない。改良案が出た場合の別系列での再評価も計画へ繋ぐ。

## この相談で変わったことと限界

次の作業順位を変更し、primaryが提案した総論の再設計を取り下げた。
配布先への導線と、既存review比較の情報履歴という別の不足が明確になった。
これは相談から得た判断材料であり、solo対照がないため、この相談の品質・速度の改善量は判定しない。
次の方式の最終選定、評価の適格性、配布先での実利用、単体を超える成果は未確認。

## 統合判断への再批判

ユーザーの「それも批判させろ」を受け、同じ3体へ`6f51f01`の統合判断を渡した。
今回は前回の統合文書を共有している。互いの第2回答は共有せず、read-onlyのまま終了した。
初回案への同調や自己案の擁護を要求せず、順位・追加費用・終了条件を批判対象にした。

| 観点 | 統合判断に残っていた問題 |
| --- | --- |
| 目的・優先順位 | 未着手であることは第一候補の根拠として不足。Cycle 002の3段階は約43〜47分、output約7〜8万で準備等は別。Cycle 003のtemplate評価と継続開発の題材を一括りにできない。監査の終了条件と、再評価までの完了条件が弱い |
| 評価・比較 | 複数実装を推した自身の前案も順位を付けすぎた。実装判断の分岐と公開選択基準が未特定。同時間の2条件で追加計算量・独立context・selectorの効果は分離できない。保存済み候補による選択監査なら生成費を省ける可能性がある |
| 実利用・配布 | 既存の知識を渡す作業まで新実験待ちにする依存関係はない。参照可能な文書を置くだけでも不十分。通常入口からagentが観測と限界を取り出せる利用確認と、性能改善の比較を分けるべき |

primaryはCycle 003の[第1段階](../../experiments/development-harness/cycle-003/large-02/phase-1.md)が
agentctlの独立acceptance実行であること、[template品質評価](../../experiments/development-harness/quality/README.md)が
別の資産であることを確認した。既存source・題材・評価・runnerを分けて再利用費を見積もる必要がある。

### 再批判を受けた採否

- **取り下げる:** 複数実装を次の第一候補と決めた順位。未測定項目の消化を採用理由にしない。
  分担を繰り上げるのでもなく、実際の未達要求と方式の作用が対応してから選ぶ。
- **先に進める:** 既存の範囲付き実測を通常の配布入口へ接続し、利用できることを確認する。
  新しい効果の発見を待たず、出典・条件・負の結果・未測定を保持する。新しい推奨規則は作らない。
  通常入口だけを与える有限の利用確認で、関連する観測と限界を取り出せることまでを中間到達点にする。
  これは性能改善や一般的な使い分けの証明ではない。
- **次の比較の選定:** Cycle 002の具体的な変更episodeを対象に、未達要求、期待する作用、
  公開検証、外部判定、必要な接続差分、結果で変える案内を対応させる。3段階全部の再演は既定にしない。
  複数実装なら有効な実装判断の分岐と公開の選択証拠が必要。分担なら独立作業境界と結合検査が必要。
- **条件付きで使う:** 保存済み候補による選択経路の監査。
  評価担当が提案した安い代替だが、候補の所在・hash・権限・評価境界を確認でき、
  新規候補生成より準備が小さい場合に使う。まだ利用可能と検証したわけではなく、新しい必須工程にしない。
- **測定の主張を限定する:** 同じ締切のワークフロー比較では全消費を併記して実用上の採否を調べる。
  usageを記録しただけで追加資源と独立性の効果を分離したとは言わない。
  分離を目的とする別の問いには、それに応じた対照が必要になる。
- **完了条件を戻す:** 配布への接続・利用確認は中間到達点。
  改良案を固定して別系列で改良前後を実行し、結果から採否を決めるまでが改善循環。
  「次の再評価を計画した」だけで循環完了とは呼ばない。

選定作業は、一件について要求・作用・公開証拠・外部判定・接続差分を特定し、
限定実装へ進むか候補を保留するか決めた時点で終える。
不足があれば合理的な要求範囲の限定で解けるかを判断し、解けなければ保留する。
広い品質の完全評価、全方式の監査、新しいrunnerの実装まで選定作業へ含めない。

queueの追加確認保留と、全面再計画を避ける判断は維持する。
第2回で方式の順位と作業順は変わったが、提案の有効性は未実測。
今回も多数決・相談回数・回答の一致を改善効果へ読み替えない。

## 難題を出発点にする再批判

ユーザーは、単独では解決・有効な案の探索・バイアスからの脱出が難しい題材を出発点にすべきで、
目的意識がずれていると指摘した。primaryは、旧計画の目的文を保ちながら校正しやすい小課題へ
実行を寄せたことと、「既知CLIの修正へ戻す」ことを次の主作業と考えた判断を修正した。

`critique_experiments`と`critique_product`へ、難度と評価、目的と実行順を分けて独立のread-only批判を依頼した。
役割によるcoverageとprimaryの判断への批判が目的。新しいlive比較や追加の実装は依頼していない。
前者は強いsoloの未達による事前の課題選定と、協働勝敗による事後選別の区別を求めた。
後者は自身の前回提案も保守へ目的を縮めたと訂正し、改善余地のあるpolicy設計/制御と、
後続の難題で改良前後を比較する工程を提案した。

primaryの採用判断:

- 主評価を高い成果水準から選び、強いsoloの不足と到達可能性を先に校正する。
- 主比較を難題に対する適応的な協働とし、固定事前相談は必要な機序を調べる補助に置く。
- 生成不足、選択損失、統合退行、共通の盲点を分け、対応するハーネス変更へ戻す。
- 第一候補は制約付き実行計画policy、次候補はsoccer、異なる難しさの候補は複合障害下の継続変更。
  優先順は仮の着手順であり、協働の有効性や課題の適格性が確認できたとは扱わない。
- 旧小課題は回帰と限定された負の観測として保持する。負の結果を増やすことを能力拡張の達成にしない。

[旧計画](../project-plan-history-through-lifecycle-relay.md)と
[旧実験計画](collaboration-experiment-plan-history-through-lifecycle-relay.md)をそのまま保存し、正本を再構成した。
8月の高難度構想から改善余地という原則を採用したが、別の開発studioを一式作る工程や数値予算は復活させない。
この相談は計画への助言であり、複数agentによる品質向上の実験証拠ではない。

書換え後の再reviewでは、評価担当は必須修正なし、目的担当はH2で原因確定を求めすぎないことと、
H1準備の終了条件を具体化することを求めた。primaryは両点を採用し、作用仮説で比較へ進む条件と、
A準備jobの120分cost cap・達成時の早期終了・未達時の保留を追記した。
この上限は次の準備枠にだけ適用し、難題の開発予算や協働の推奨値にはしない。
