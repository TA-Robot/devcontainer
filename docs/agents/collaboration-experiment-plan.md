# 協働実験計画: 難題の未達から方式とハーネスを改善する

更新: 2026-09-08。[目的と工程の正本](../project-plan.md)に従う。
[以前の方式比較計画](collaboration-experiment-plan-history-through-lifecycle-relay.md)は実施履歴として保存する。
旧実験を再開・再採点する計画ではない。新しい主評価のlive protocolはまだ固定していない。
[H2初回のsolo校正](../../experiments/development-harness/scheduling/solo_v1/result.md)は2回とも参照水準へ到達。
この版ではG3の単独未達を確認できずH3へ進めない。次候補の成果水準と適格性を先に確認する。

## 研究の問いと測定対象

欲しいのは、強い単独でも探索・判断・実装が行き詰まる課題で、協働が到達可能な成果を広げること。
主評価の単位は一つの成果物を探索・実装・選択・統合・検証する開発episode、
または実状態を引き継ぐ要求変更系列とする。個々のtestや候補を独立sampleとして水増ししない。

主に以下を問う。

- 単独が未達だった要求や実用上の性能水準に到達するか。
- 同じ締切で得られる成果の質は上がるか。追加総消費に見合うか。
- 良い案を生む、誤った仮説を棄却する、案を選ぶ、統合する、のどこが変わったか。
- その不足に応じたハーネス改良が、未使用の難題でも成果を改善するか。

方式の全体効果と個別作用の説明は分ける。最初から全要因を分離する巨大実験を組まない。

## 難しさを成果へ結び付ける

| 課題の構造 | 必要な設計 | 難度を偽るもの |
| --- | --- | --- |
| 広い設計・戦術の探索 | 実質的に異なる有効解があり、条件によって優劣が変わる。試作で差を検査できる | 用語だけ違う案、唯一の指定解法、機能一覧を長くするだけ |
| 因果の曖昧さ | 複数の説明が初期観測と整合し、公開の追加実験で区別できる | 正解に必要な情報を全員から隠す、評価者だけが知る謎解き |
| 結合した制約 | 局所最適な変更が別の要求に影響し、統合後の動作を評価できる | 独立小問の大量詰合せ、単にfileを増やす |
| 改善余地のある性能 | 最低限の動作後も有用な差があり、複数条件で外部測定できる | 基本APIが動けば満点、速度noiseだけで設計差を認定 |
| 継続性と変化 | 初期成果の実状態と設計判断が後の要求を左右する | 毎段階で正解実装へ交換、後から隠れた要件を追加 |
| 反証と頑健性 | 公開条件だけへの過適合や共通の誤りを未使用条件で検出できる | seedや名前だけ変えて別分野への一般化と呼ぶ |

最低限の実行・安全・互換性は必須条件として保持する。その合格を品質全体の100点にしない。
絶対最適値が不明でも、公開された到達水準と意味ある品質の比較が可能なら対象にできる。
創造的な案は、試せる仕組み・予測・実装へ落として成果を測る。案の魅力をLLMの好みで順位付けしない。

## 主評価へ入れるゲート

以下は主評価の妥当性を守るhard guard。scopeは新しい難題の採否、ownerはprimary/integrator。
根拠は「単独を超える成果」を測ること。通過の証拠が崩れたら課題を保留し、版を分けて再設計する。
同じrunの条件や得点を修正して合格にしない。

| ゲート | 必要な証拠 | 不成立時の処置 |
| --- | --- | --- |
| G1: 欲しい成果 | 利用上の価値、公開要求、重大制約、到達水準が具体的 | 方式やrunnerから作った課題を主評価にしない |
| G2: 解ける・測れる | 実行可能なreference/構成的な有効解、異なる妥当解、実効性のない解の拒否 | 解なし・情報不足・oracle不良を難度に数えない。局所校正だけ直す |
| G3: 強いsoloの改善余地 | 開発用課題で複数案・再考・検証・逐次試作を許しても残る未達や停滞 | 容易なら回帰・低難度対照へ。予算やtoolを不当に削って未達を作らない |
| G4: 協働で変え得る障害 | 探索不足、仮説の固着、選択、統合等の観測と対応する作用仮説 | 「難しいから人数追加」では採用しない。全員同じ誤りの可能性も記録 |
| G5: 選定と確認の分離 | 課題候補・除外・開発用と未使用評価の境界・停止方針の固定 | 協働の勝敗を見て課題・閾値・seedを選ばない |
| G6: 到達と費用の回収 | 実際の提出物、候補、選択、統合、全開始run・全呼出し費用を結ぶ | 事後最高候補を提出結果にしない。欠測・未回収を成功にしない |

主評価への適格性と、実験実装のsmoke test成功を別々に記録する。
校正用に旧queue/relayを再利用しても、それでG3を満たしたことにはならない。
G4は観測された未達に対応する作用仮説を求める。未達原因の因果的な確定まで校正の通過条件にせず、
比較によって仮説を検査する。主要な妥当性条件が揃えば、詳細な診断や汎用化を待たず主比較へ進む。

## 強いsoloの難度校正

開発用の課題集合を先に列挙し、公開条件、資源方針、候補数、終了条件を固定する。
soloには同じ公開情報・toolを与え、自己review、複数案、ローカル検索、再試作、公開実験を許す。
単独は一つの推論主体として定義し、別の独立LLMへの要求は協働側に数える。
通常の非agent tool、solver、テスト生成の利用を禁止して難しくしない。

初期解が動いた後の品質、追加探索での改善、まだ残る未達を観測する。
時間不足か探索方法の停滞かを区別する必要がある場合は、より大きいsolo予算を有限に事前登録する。
強いsoloが早期に満点なら、主評価へ残すための局所的な意地悪条件を後付けしない。
公開された実要求に基づく課題系列の改訂として、別の未使用条件へ移す。

一回の失敗だけで安定した限界と断定しない。予備実行で費用とばらつきを把握し、
意思決定に必要な再現性を確かめる範囲を固定する。安定性が不明なら「校正未確定」と記録する。
成功率の目標値、何倍難しいか、必要人数、何分なら難題かを全体の定数にしない。

単独が未達だった開発用の課題層を主対象に選ぶことは、今回の目的に合っている。
その選定を協働結果より先に行い、結論はその層へ限定する。
確認側で成功したsolo runを除外したり、失敗したsoloに対応する組だけを主集計に残したりしない。

## 開発・探索・確認のデータ境界

| 集合 | 用途 | 見せてよいもの・禁止する再利用 |
| --- | --- | --- |
| 公開開発 | 仕様理解、試作、実験、実装の修正 | 両条件が同じ検査能力を使う。hiddenの答えを公開feedbackとして流さない |
| 難度校正・方式探索 | soloの不足、課題の識別力、方式と予算の設計 | 選定履歴と失敗も保存。既知課題なので確認性能には混ぜない |
| 未使用の確認 | 固定した方式・ハーネスの最終比較 | 問題の領域と評価軸は公開し、具体例・障害順序・workloadは開発側から隔離 |
| 別系列・継続開発 | 適用範囲、変更への対応、負の転移 | 名前や乱数だけの変更と、構造・分野の違いを区別 |

課題を作ったりoracleを読んだagentを、そのまま未見の開発担当にしない。
過去成果・reference・評価の所在をactor環境から除き、sourceと入力を固定する。
評価器へアクセスした組織全体が未知になるわけではないので、誰がどの内容を見たかも境界として残す。

## 主比較と補助比較

### 主比較: 難題に対して協働を組み立てる

- 強いsolo: 自己検証、複数案、逐次試作、修正を選びながら成果へ進む。
- 協働ハーネス: 同じ公開能力に加え、相談、独立案、競合試作、独立検証、分担・統合を状況に応じて選ぶ。

初回は同じ締切での到達力を主に測り、追加の全消費を併記する。
同時間を同費用、独立性だけの効果、最適人数の証明とは呼ばない。
課題の障害に対応する方式の使い方を提供するが、固定のadvisor起動や全方式の使用を強制しない。
未発動も割付結果に残す。低難度の対照は過剰協働の退行確認に使い、難題の結果と混ぜて主結果にしない。

### 補助比較: 何が効いたか・どこが壊れたか

| 観測した不足 | 必要なら行う比較 | 変更先 |
| --- | --- | --- |
| 同じ解法ばかり | 単独の複数案 / 独立した案の探索。問題の分け方や共有する初期結論を変える | 発想を求めるbrief、独立性、探索予算 |
| 反証を取らない | 自己調査 / 独立診断と反証probe。暫定説の共有時点を変える | 相談の起動条件、証拠要求、仮説の更新 |
| 良い候補を選べない | 同じ保存候補を固定し、公開の選択手順だけ比較 | 共通実験、比較する条件、選択へのreview |
| 統合で品質を失う | 同じ候補・境界で、統合と再検証の手順を比較 | 所有権、context引継ぎ、統合後check |
| 追加費用だけが増える | 予算配分、段階的な候補絞込み、停止条件を比較 | 起動・継続・終了の判断 |

同じ候補集合の比較は選択の診断であり、案を生む能力の測定とは区別する。
独立した実装を比較する課題を、保存された候補の分類だけに縮小しない。

追加資源自体の効果が採否に重要なら、総資源を増やしたsoloや、独立試行を逐次実行する対照を置く。
独立したLLM試行のbest-of-Nは複数探索の対照であり、継続する一つのsoloと同じものではない。
並列化と探索の独立性を区別したい場合に使う。初回から全対照を総当たりしない。

## 生成・選択・統合を分けて観測する

開発担当は公開の証拠で候補を選び、選択理由とartifactを固定して提出する。
hidden評価は最終提出の後に行う。診断のため全候補を採点する場合も、その結果を選び直しに返さない。

| 最終結果の原因候補 | 必要な観測 |
| --- | --- |
| 良い候補を作れなかった | 各候補の実装/試作、異なる仮説、終了後の要求別評価 |
| 良い候補はあったが選べなかった | 公開での比較記録、固定した選択、事後の候補評価 |
| 選べたが統合で壊れた | 選択前後のhash、統合diff、同じ条件での外部評価 |
| 全員が同じ誤りをした | 候補別の失敗領域、共有情報、反例の有無 |
| 良い助言が成果へ届かなかった | 助言の証拠ID、対応するtest/変更、最終成果への反映。不明な因果はunknown |

事後最高候補は「作られた集合にあった可能性」の上限としてのみ報告する。
多目的品質で一つの最高値を決められない場合、満たせた要求や非劣な候補集合を保持する。
候補の良い部分を混ぜたものは新しい成果として再検証し、各候補の得点を足し合わせない。

固着を調べる場合、公開で取得可能な反証、取得した時点、次の行動・test・artifactの変化を使う。
内的思考や自己申告の確信度を必須の観測にしない。
異なるagentが同じmodelでも、異なる解法や証拠を得たとは限らない。役名や人数で多様性を認定しない。

## 評価器と到達曲線

外部評価は候補の自己申告値を真実として受理しない。候補が共有状態を書き換えて評価条件を変える経路も閉じる。
正しい別実装を受理し、無効な仕組み、過適合、性能値の捏造、見せかけの成功を拒否できるか校正する。
自由文の真偽を自動判定できなければその軸をunknownにし、文章の分類一致を実装品質へ置き換えない。

課題ごとに、必須保証と性能・頑健性・変更対応のvectorを固定する。
平均だけで成功とせず、重要な条件群と厳しい条件での結果を残す。
利用価値に基づく到達水準を比較前に決め、協働の点数を見てから閾値を下げない。

品質と予算の関係が必要なら、事前に選んだ観測点または別予算の有限runを使う。
書込み中の無停止copyを整合した成果と仮定せず、既存の提出・停止・snapshot方式を使う。
粗い観測から初回成功時刻を補間しない。単独未達を上限時刻の「遅い完成」にしない。

## 予算と停止

実行前に、課題・source・評価器・ハーネス・model/effort・公開tool・権限・割付順・全run数・
全呼出し時間/usage・公開検証費・選択/統合/最終評価費・保存量・cleanup・欠測方針を固定する。
今回の計画段階では、適格性と実行費用が未確定なため数値のlive予約を置かない。
次のH1/H2 protocolで値を確定し、未知のまま実行しない。ユーザーへ定型の予算記入を求めない。

数値の役割はcost cap、探索配分のplanning prior、未検証のhypothesisに分ける。
scopeは当該課題系列、rationaleは実測した実行費用と判断に必要な精度、ownerはprimary/integrator。
費用・ばらつき・識別力が想定と異なる場合は次版で見直す。今回runの上限を延長して勝つまで試さない。

不要な同一検証の再実行は避けるが、難題の探索・失敗・複数案の試作に必要な予算は主作業として確保する。
準備費を抑えるために、複数実装を読むだけに変える、探索を禁止するなど、測る能力を削らない。
全停止、未知usage、保全の規則は[評価方針](development-harness-evaluation.md)を維持する。

## H4/H5: 観測をハーネスの変更と再評価にする

実測を説明文へ追記しただけで改善循環を閉じない。
例えば有効な別案が出なければ独立探索のbriefと比較前の情報共有を変え、
有効案を捨てたなら公開検証と選択手順を変え、統合退行なら境界・引継ぎ・最終検査を変える。
変更対象は既存のorchestration skill、playbook、native role、実行制御から必要な箇所だけ選ぶ。
機序を測るためだけの巨大な汎用会話基盤は作らない。

確認では同じ協働能力を持つ改良前ハーネスと改良後ハーネスを比較し、
難度校正・方式探索に使っていない条件を使う。strong soloの基準も失わない。
通常入口から情報が使われることと、その利用で成果が改善することをそれぞれ検証する。

到達改善がなければ能力拡張は未達と記録する。両側未達なら、解の生成、選択、統合、評価のどこで止まったかを確認する。
協働の失敗は「もっと人数を増やす」「もっと難しくする」「もっと簡単にする」の自動的な理由ではない。
次に変える要因は観測された不足から選ぶ。適用範囲付きの正・負・不明と未着手を残し、追加runの採否を決める。
