# プロジェクト計画: 協働を、難しい開発成果へ結び付ける

更新: 2026-09-23。ユーザーの再検討依頼に基づき、次の優先順位を変更した。
**スケジューリングの次pair接続を自動的な次手にせず、既存の実リポジトリ課題で、
現在の強い単独の未達と、協働で変えられる不足を確かめる。**
直前までの計画と全経過は[履歴](project-plan-history-through-runtime-readiness.md)へ保存した。
判断の根拠・代案・反証条件は[今回の再レビュー](project-review-2026-09-23.md)。
本書が目的・実行順・到達条件の正本である。

## 目的と完成の意味

難しいソフトウェア開発で、強い単独agentが探索・実装・検証・統合しきれない成果へ、
必要に応じた相談、独立探索、反証、分担によって到達する。その手順をこのdevcontainerから再利用できるようにする。

完成を示すのは、**実際に選択・統合された成果物が、事前に決めた有用な要求を満たし、
同条件の強い単独を超え、その改善が別の未使用課題でも確認されること**。
モデル更新、実験の完走、採点可能化、参加者数、文書量は完成条件ではない。
単独が既に解くものを、tool・時間・effortを削って難題にしない。
協働が必ず勝つとは仮定せず、単純なモデル選択だけで十分なら、より安い改善として採用する。

全世界の最短経路や最適な協働方式を証明する計画ではない。
次の判断を変える証拠までの準備費・実行費・人の確認費を減らすことを優先する。

## 現在地

| 項目 | 確認済み | 残る不足 |
| --- | --- | --- |
| 開発基盤 | stable/edge、native agent template、agentctl、project lifecycle、Mira、観測・検索入口 | 更新CLIでの互換性維持。新モデルの利用可否と実適用は別確認 |
| 動的scheduling | 標準協働・改良協働・単独の3成果物を独立評価 | 改良版11637/560、単独11822/567（価値/最重要完了）。能力拡張は未達、協働usageもpartial |
| 継続開発 | 強い初期sourceの共有と公開校正 | 元pairは単独の期限停止で保留。協働は未開始、旧枠は閉じている |
| 時計・回収 | 期限後captureと起動完了後の応答時計を実装。新時計の4試験・公開24例ずつの照合は通過 | 新しい実比較へは未接続。接続する価値自体を今回再判断する |
| 主評価 | 協働一般の有効性・費用効率は未確認 | 一つの最適化課題での微差から、開発ハーネスの有用性へ一般化できない |

モデル・CLI更新は[運用更新記録](agents/model-refresh-2026-09-23.md)を参照。
GPT-6 Sol、Grok 4.7、Claude Opus 5.5の登場だけで、旧測定や強い単独の基準を置き換えない。

## 今回変えること

1. **課題・採点器の自作を主工程から外す。** 外部の実コード、公開要求、既存の独立動作評価を借りる。
   第一候補はSWE-Bench Pro V2の難題部分集合から選んだ少数の開発課題。
   公開benchmarkの難度・正解を無条件に信用せず、空patch/reference/妥当な別解の境界を確認する。
2. **最初に単独の失敗を観測する。** 現在のモデルと十分な開発能力で調べ、
   基盤不良、説明とtestの矛盾、到達可能な開発上の未達を分ける。
3. **同じ失敗の先を、単独継続と協働継続で比較する。** 同じ保存source・公開実験・残る要求から再開し、
   単独にも追加探索・複数案・自己反証を許す。長い「よく考えよ」指示だけの比較を繰り返さない。
4. **結果から最小のハーネス変更を選ぶ。** 影響範囲の見落とし、誤診断、候補不足、統合失敗のうち、
   実際の不足を一つ変える。通常配布は、別課題での確認を経て行う。

## 次の有限milestone

外部課題の選定・固定sourceは[実リポジトリ課題の入口](agents/repository-task-pilot-2026-09-23.md)。
以下は今回のplanning priorで、ownerはprimary/integrator。費用と能力の確認で更新する。
liveの開始数・全費用・source一致検証を固定するまでは、実モデル比較を開始しない。

| 段階 | 実施すること | 完了・停止条件 |
| --- | --- | --- |
| R0: 更新を使える状態にする | CLI配布更新、新モデルの設定入口、既存の回帰確認 | imageとwrapperが動き、モデル・effort・権限の根拠を区別できる。新しい評価基盤は作らない |
| R1: 既存難題を一つ実行可能にする | 固定した候補順でimage・要求・独立採点を点検。既存の回収を必要な範囲だけ接続 | 空patchは失敗、referenceは成功し、actorへ正解・非公開testが見えない。初回はAnsible候補から。準備が膨らむ場合は不足を残して停止 |
| R2: 現在の単独の未達を確認 | 最大3候補を固定順でstrong soloが開発。途中sourceと公開検証を保全 | 最初の適格な未達を選ぶ。成功例・除外理由も全て保存。全て解けたら協働を追加せず、この課題層を不採用にする |
| R3: 不足に対応した一組の探索 | 選択済みcheckpointから単独継続と協働継続。両成果物を封印してから同じ独立評価 | 最終要求充足・退行・全資源を比較。新しい証拠を伴う実装変更を診断し、説明の良さを採点しない |
| R4: 改善の確認と配布 | 有効だった介入だけを別課題・別repoで、同じ強い単独と比較 | 未使用課題の改善と退行を含めて採否を決め、skill/playbookへ最小限反映。R3の勝ちだけで一般推奨しない |

R1の準備は最初の一件について120分のcost cap（取得・校正・接続を含む経過時間）。
既製imageと評価器で省ける工程を確認するための上限で、開発能力の時間制限ではない。
不足が大きければ、別の汎用runnerを書き始めず、どの再利用仮説が外れたかを記録して再判断する。
R2の3候補は探索費用のcap。上流の50分/開発はplanning priorであり、このプロジェクトのlive枠ではない。
本番の時間・全参加者費用・評価費・停止・回収上限は、R1の実測から一件のprotocolに固定する。

## 比較で混ぜないもの

- 強い単独は特定のmodel/effort/CLI/tool/資源を持つ条件であり、「最強モデル一般」とは呼ばない。
  Astraを最初の候補とし、Solへの切替だけで対照を弱くしない。Claude/Grokの能力も旧版から推測しない。
- 異なるproviderとの協働は有望な仮説だが、モデル変更と協働構造の効果が同時に変わる。
  別provider単独で足りるならモデル選択を優先し、純粋な協働効果とは言わない。
- `high`、token数、subscription枠はprovider間で同じ計算量・費用を意味しない。
  同じ経過時間での品質と、総費用を揃えた比較を分ける。usage欠測は費用不明のまま残す。
- 公開benchmarkは学習への混入を否定できない。外部評価testを非公開にしても、世界に未公開の課題にはならない。
  新seedだけを別課題と呼ばず、一般化の主張には別repo/別要求の確認が必要。
- 重要な退行を平均値で隠さない。一方で事後に追加した要求や、模範実装と違うだけの理由では不合格にしない。

## 今回優先しないこと

- schedulingの新しいpair、同じ系列の新seed、候補選択UI、汎用collector、別のAI開発studio。
- soccerへの自動的な題材変更。既存の[入口監査](agents/soccer-candidate-entry-audit-2026-09-08.md)で評価境界の不足がある。
- 全モデル・全effort・全協働方式の総当たり、duration atlas全件の再計測。
- CLI対応と同時に旧実験actor・固定model catalog・得点を変更すること。

これらを禁止する一般則ではなく、今回の目的に対する優先順位である。
再開する場合は、必要な証拠・準備費・今回の経路より短い理由を示す。

## 保持する資産と原則

過去のprotocol・oracle・開始台帳・得点・保留は変更しない。
schedulingは、最適化の補助課題と時計・隔離・回収の回帰資産として残す。
terminal/native回収・agentctl・templateは、実在する能力だけ必要な範囲で再利用する。
新しい依存は通常imageへ無条件に入れず、評価専用環境へ分け、導入理由と撤去手順を残す。

協働の設計は[collaboration model](agents/collaboration-model.md)、
適格性・比較原則は[実験計画](agents/collaboration-experiment-plan.md)、
過去の実測は[collaboration evidence](agents/collaboration-evidence.md)を参照する。
この計画変更自体は、能力拡張の達成でも、次の実験の成功でもない。
