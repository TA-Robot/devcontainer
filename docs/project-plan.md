# 開発ハーネスの現行計画

更新: 2026-09-05。ユーザーが承認した目的は、このdevcontainer上で実開発を効率よく進められる環境を作り、定量評価と改良を繰り返すこと。Evidence Forge／ForgeRoom製品の完成は目的から外す。過去の[レビュー](project-review-2026-09-05.md)は履歴として保存する。

## 方針

実際に必要な保守・開発作業を進め、その過程の足止めを解消する。速度向上と品質向上をそれぞれ目的にする。同じ品質まで早く到達する価値と、同じ時間・費用でより良い成果を得る価値を分けて評価する。native agent、既存のGit・job管理、有限実行を活用し、独自の対話製品や総当たりbenchmarkを先に作らない。使わない評価器は修復を必須にしない。

**小規模と大規模を両方評価する。** 小規模での数分の修正だけでは、継続的な機能開発の設計・仕様変更・再開・統合を評価できない。両規模の結果を分けて報告し、継続開発の実測も採否に使う。規模、比較単位、指標、予算候補は[規模別評価方針](agents/development-harness-evaluation.md)を正本とする。

## 最初のサイクル（小規模・完了）

計画・現状評価・改良候補の比較・実装・実際の開発試行・再評価・採否までを実施する。詳細と事前の測定条件は[cycle-001](../experiments/development-harness/cycle-001/protocol.md)。

1. 実際の標準imageで必須checkとcheckout側コードの検証経路を確認する。
2. 同じimmutable sourceと同じ開発taskを、初期環境で実際のCodexに実行させる。
3. 観測された環境起因の阻害要因を修正し、対象の回帰・plain/frozen imageを検証する。
4. 同じtask・model・effort・権限で改良後を実行する。candidateの自己申告に依存せず、外側で成果と実行記録を検証する。
5. 正しさ、必須check完遂、時間、usage、復旧作業、scope逸脱を報告し、採用・棄却・不確定を判断する。
6. 実用的なcandidate修正をprimaryがreview/integrateし、次の問いを残す。

## Cycle 001の現状評価で見つかった優先事項

- 標準imageはPython 3.10だが、必須template validatorがPython 3.11の`tomllib`を無条件importし起動できない。
- checkout側`scripts/agentctl`が、隣の編集対象libraryよりinstalled libraryを優先する。テスト対象が編集したコードと一致しない可能性がある。
- supervisorのlog縮小と保持metadataのpublicationに時間差があり、現行testは後者を待たず失敗する。

最初に予定していた「testの待合せ修正」より、環境と検証対象の一致を優先する。これは今回実測した問題に基づく計画変更である。

## 判断基準

意味的品質とユーザー変更の保持はtaskごとのhard guard。品質は足切りだけでなく、機能の正しさ、保全・堅牢性、利用・運用、変更・保守の観点で向上を評価する。速度は固定した品質水準への到達率・時間、品質は固定した予算時点の成果で比較し、両規模それぞれで報告する。遅くても品質が高ければ、その向上と追加費用を採否に使う。timeout、未実行、モデルによる自己申告、外側の実測を区別する。少数runの差を一般的な開発効率や全modelの推奨値に拡張しない。

source/import、依存の互換性、非同期publicationのような決定的な不具合は局所再現で採否を決められる。開発時間の差は探索的な観測であり、必要なら別taskの反復を次cycleにする。悪い結果が出た場合も計画を修正して進め、成功結果が出るまで無制限にrunを追加しない。

## Cycle 001で得た判断

計画・現状評価・改良・実試行・再評価・成果の取り込みを完了。取り込み後の固定依存コンテナで121/121 test、通常／固定依存buildと起動hookの確認が成功した。

実際の保守taskを同じmodel・CLI・権限で実行し、外部の意味的評価は改良前後とも33/33。所要時間は379.449秒から235.089秒へ短縮した。この1組の約38%差は探索的な観測値であり、一般的な速度改善や投資回収の証明にはしない。詳細・失敗履歴・最終検証は[結果報告](agents/development-harness-cycle-001.md)と[機械可読結果](../experiments/development-harness/cycle-001/result.json)を正本とする。

採用するのは、checkoutと実行コードの一致、同梱Pythonで動くvalidator、選択modelに対応するCLI、実際のmount元や非同期完了を確認するtest修正。実作業で生成した非有限JSON数値の拒否処理もreviewして取り込む。これらの決定的な不具合の再現・修復が採用根拠であり、速度差だけで採用しない。

Cycle 001は小規模の予備評価として位置づける。この時点では大規模への有効性は未評価であり、「次は複数componentの変更を一件」だけでは不足する。今回の修正をbaselineとして固定し、同じ開発対象を設計から利用・追加要求・統合まで発展させる大規模評価を準備する。

## Cycle 002（両規模の評価・完了、大規模を先行）

1. [課題選定メモ](../experiments/development-harness/multi-scale/task-selection.md)から実需要のある大規模taskを確定する。別projectへの導入・既存設定を保持する継続更新・中断復旧までを一つの利用経路として完成させる開発を[大規模01](../experiments/development-harness/multi-scale/large-01/protocol.md)として選定した。段階要求と受入シナリオは固定済み。機能の最終採用は成果の検証後に判断する。
2. 公開要求と段階的な追加要求、外部の受入検証、予算時点、停止・再開条件を比較前に固定する。時間やfile数を増やすだけの難化はしない。
3. 大規模向けのsnapshot・段階実行・累積計測を必要な範囲で実装し、provider-freeで停止と証跡保持を検証する。cycle-001の900秒・単発runnerを長時間開発対応済みとは扱わない。
4. 大規模の現状評価から改善候補を選び、実装・再評価する。完成率に加え、時間内の到達品質、追加要求への対応、退行、再開・統合、人間の介入、総費用を記録する。
5. 同じ介入を新しい小規模taskでも評価し、局所作業に余計な負担を増やしていないか確認する。両規模の結果と未解決事項を揃えて採否を決める。

段階実行・snapshot・累積計測・外部のCLI検証を実装し、fake providerと実Dockerで
事前検証してから、小規模1組・継続開発3段階1組を完了した。結果は
[cycle-002報告](agents/development-harness-cycle-002.md)を正本とする。

小規模は312.563→347.433秒、継続開発は2,553.708→2,825.146秒で、今回の
環境介入による時間短縮は確認できなかった。固定シナリオは両条件で21/21、35/35だが、
追加レビューでは継続開発の改良側に採用時のpermission要求の未達があり、
全要求を満たす成果同士の速度比較とも扱わない。

採用根拠は、Dev Container CLIの事前同梱、Docker接続前提の明示、実際に再利用される
build cache、および成果の保守上の価値である。時間差だけで採用しない。
公開仕様を満たす対照成果からtemplate lifecycleと閾値修正を取り込み、
統合時にはGitへの管理データ混入、配置先の重複判定、doctorの版の誤判定を修正した。
統合版は146テスト、両規模の外部シナリオ、旧状態からの移行、通常／固定依存buildと
起動確認を通過した。測定後の統合修正の速度効果は未測定である。

## 次のサイクルの優先順位

1. **速度と品質を別々に検証する評価条件。** 両規模の実需要に対し、品質の各項目、
   同じ品質への到達条件、同時間のsnapshot、公開要求を揃える方法、停止規則を固定する。
   公開仕様を満たさない成果を識別できるよう評価器を校正する。cycle-002の35/35を
   高品質の上限とみなさず、品質向上を測れる範囲か確認してから次のlive比較へ進む。
2. **開発エージェント自身が必須確認を完遂できる経路。** Unix socketとDockerに
   関する実行環境の制約が両規模で再現した。CLIの存在や外側doctorの成功では足りない。
   実際に開発commandが走る権限・mountで能力を確認し、不足だけを解消する。
   介入の仮説は「検証待ちを減らして速くする」と「検証を使って欠陥・退行を減らす」に
   分ける。検証が起動したことと、提出物の品質が上がったことを別に確認する。
3. **異なる課題での再現性。** 数値検証の修正以外の小規模taskと、複数componentの
   設計・変更・移行・利用までを含む継続開発を用意する。週単位の大規模projectへの
   有効性は今回未確認。時間を浪費させることを難度の代用にしない。
4. **品質と完遂までの費用。** 固定シナリオ、追加レビュー、内側の必須check完遂、
   外側の検証・統合負担を分ける。30分snapshotの通過をrelease完了とみなさない。
   開発sessionだけでなく、準備・外部検証・統合・配布確認の開始／終了も自動記録する。
   並行作業の時間を単純に足さず、利用可能になるまでの経過時間と作業別の費用を分ける。
   未計測の過去の統合・人間review時間は推定で埋めない。
   一般的な速度・品質効果を問う比較は反復数・実行順を事前に決める。

独自の汎用実行brokerや大きなbenchmark製品の追加を、上記不足への既定解にしない。
次cycleの実装範囲は実際の能力確認に基づいて決める。今回の結果を良く見せるための
追加live試行は行わない。

### Cycle 003の判断と残作業

要求単位の[品質評価器](../experiments/development-harness/quality/README.md)を実装し、
前回の3成果へ同じ検査を実行した。従来の35/35では見えなかった権限・配置境界・
Git運用の差を識別できた。保守性と案内に沿った利用は未測定として残している。

固定版Codexのローカル能力probeと、同じ既存supervisorテストの比較では、
workspaceの通信制限によってUnix socketを使う検証が阻害されることを確認した。
比較用の通信許可profileではテスト2件が通るが、通常運用の設定は変更していない。
Docker readinessの一時timeoutで早期終了する不具合は修正し、期限・再試行を検証した。

新しいJSONログ修正で小規模1組を実行した。提出時間は対照567.601秒、改良435.743秒。
約120秒のsnapshotでは改良側だけが固定の品質条件を満たし、約240秒では両方が満たした。
固定19件の最終結果は両方合格だが、追加レビューでは対照側の伏せ字漏れと、
両案共通のUTF-8出力不具合を識別した。改良案を修正して取り込み、core回帰66件が通った。
詳細と配布確認の状態は[cycle-003報告](agents/development-harness-cycle-003.md)、
原観測は[小規模の結果](../experiments/development-harness/cycle-003/small-result.json)。

今回の約23.2%短縮は1組の探索的観測であり、継続開発の効果には外挿しない。
検証commandのnetwork権限を広げた比較なので、全利用者の既定権限を変更する根拠にも
しない。採用は再現した不具合の修復に基づき、速度と品質の一般的な効果は分けて保留する。

次の優先は、[独立したacceptance実行](../experiments/development-harness/cycle-003/large-02/README.md)
の継続開発である。現在のjob検証が、実際には失敗するcommandをモデルの成功報告だけで
受け入れることをfake providerの実jobで再現した。実行・証拠の鮮度・中断と配布の
3段階へ分け、後続変更で以前の性質が維持できるかも測る。全41観測の外部評価器を
実行可能なreferenceと誤実装で校正した。配布版は実際のimage内の13観測で別に確認する。
[事前protocol](../experiments/development-harness/cycle-003/large-02/protocol.md)で
旧状態、有限予算、要求の公開条件、時点比較と未完了の扱いを固定した。
新しい汎用schedulerの開発へは広げない。

配布確認では、コードを取り込んだbase imageの後段でDocker-in-Docker Featureの
インストールが再実行され、APT索引48.2 MBの取得だけで10分17秒を要した。
モデル開発時間には含めていないが、実際に利用可能になるまでの足止めである。
共通環境は同じ署名付きAPT archiveをHTTPSで取得するよう修正し、通常／固定依存buildと
導入package一覧の一致を確認した。OCI cacheでソース変更時のtoolchain層再利用も確認した。
再起動時の一時領域とDocker/cacheの準備待ちを揃え、その費用はモデル時間から分ける。
両条件へ同じcacheを供給し、既存の公式Feature、固定版、sourceなしの配布確認を維持する。
単発の通信遅延やcache試行から一般的な短縮率は推定しない。

## 後順位

ForgeRoom、G3難化、全面的なtelemetry、atlas routing、定期agent、強いLane I、新しい汎用frameworkは、実際の開発に必要な不足が確認されてから再検討する。現在のtrust境界とunknownの扱いは維持する。既存の未追跡実験・raw証跡は削除・一括公開しない。

更新責任はprimary/integrator。ユーザーへ日報や形式的な再承認を要求せず、結果が次の優先順位を変えた時に説明する。
