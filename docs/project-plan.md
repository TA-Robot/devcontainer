更新: 2026-09-09。fresh単独/adaptiveの原比較保留、固定成果物の診断、次の回収修正まで反映した。
この文書が目的・優先順位・到達条件の正本。
[直前の計画](project-plan-history-through-lifecycle-relay.md)と

## 出発点

**難しく、強い単独agentでも良い解を発見・選択・実装・検証しきれない課題がある。
異なるagentとの相談、独立した探索、多様な案、競合する実装、反証と統合によって、
そこへ届くようにする。その能力を自動評価で確かめ、開発ハーネスを改善する。**

まず欲しい高い成果水準と、その到達を妨げる難しさを置く。
「今あるrunnerで採点できる」「簡単な対照実験を一組作れる」から題材を選ばない。
強いsoloにも改善余地が残る課題を主評価の中心に据える。

ここでの「単独では届かない」は、公開情報・tool・model条件・資源方針を明示した上での未達を指す。
単独の自己検証、再考、複数案、逐次試作を許した上で、それでも何が足りないかを調べる。
単独の絶対的不可能性を証明してから研究する必要はない。
一方で、協働にすれば必ず解けるとも仮定しない。全員が同じ盲点にはまることも評価対象にする。

難題の選定と協働による成功は別の判断である。
**単独の不足を校正して課題を選ぶことは必要。協働が勝った課題だけを後から選ぶことはしない。**

## 今回修正する目的のずれ

目的文には能力拡張を書いていたが、実行順では校正済み小課題・既存oracleへの接続を優先していた。
queueや保存候補の分類で両者が満点になり、時間差や相談の追加費用が主な結果になった。
これらは実行経路と低難度での不要な協働を調べる材料だが、難題への到達力を評価したことにはならない。

「負の結果も価値がある」は正しい。しかし、到達余地のない課題で負の結果を増やしても、
このプロジェクトの中心的な不確実性は減らない。既知CLIの保守へ戻すだけでも同じ不足が残る。
今回の改訂は方式表の追加ではなく、主評価へ入れる条件と、何を進捗と呼ぶかの変更である。

8月の[高い改善余地を持つ課題の検討](../temp/deep-development-benchmark-redesign-20260830/01-properties-of-a-high-ceiling-task.md)には、
最低限動いた後にも設計・実験・修正で成果が伸びる必要性が既にあった。この原則を正本へ戻す。
参照先はローカルの探索メモであり、必要な判断は本書へ取り込み、実行時の依存にはしない。
当時の数値予算や、別のAI開発studioを一式作る計画は引き継がない。
現在のdevcontainerから直接難題の成果物を開発し、外部評価する。

## 越えたい単独の限界

| 難しさ | 単独で起こり得る停滞 | 協働で試す作用 | 最後に必要な成果 |
| --- | --- | --- | --- |
| 解法の探索が広い | 最初に動いた設計の局所改善を続け、別の解法へ移れない | 独立案、異なる問題分解、安い試作と比較 | 未使用条件でより強い実装 |
| もっともらしい説明が誤っている | 初期仮説を補強する検査を繰り返し、反例を取り逃す | 暫定結論を見ない独立診断、反証実験、証拠交換 | 原因の再現と修正、関連する退行の解消 |
| 多数の制約が相互作用する | 各部分は正しいが、全体では資源・互換性・境界条件が破綻する | 観点別の検討、制約の突合せ、実装後の独立検査 | 結合した受入条件を満たす成果 |
| 良い案を見分けにくい | 自分の案や説明の上手い案を選び、実測に負ける | 共通の公開実験、反例条件での比較、選択への批判 | 実際に選択・統合した成果の改善 |
| 長い開発で初期判断が重い | 局所修正が積み重なり、仕様変更に対応できない | 独立した設計案、境界を分けた試作、統合と再検証 | 状態を引き継いだ後続要求への到達 |
| 検証すべき状況が多い | 一部の成功例へ過適合し、失敗領域を見落とす | 異なる失敗領域の探索、反例生成、競合仮説の検査 | 広い条件と厳しい条件での安定した性能 |

人数や会話を増やすこと自体は作用ではない。
同じ案を別の言葉で返す、全員が同じ公開checkだけを見る、多数決で誤りを固める失敗も残す。
「バイアス」は内心を推測して採点せず、公開反証を得ても実装・判断が変わらないなどの観測で扱う。

## 評価の中心

主に知りたいのは、単独では未達だった実用的な到達水準を越えられるか、
そして同じ資源方針の下でどこまで良い成果が得られるかである。
正しさの必須条件だけでなく、条件への頑健性、制約下の性能、後続変更への対応を課題ごとに評価する。
一つの総合点で重大な不具合を速さや平均値と相殺しない。

| 評価するもの | 扱い |
| --- | --- |
| 最終成果の到達・未達 | 主指標。選択・統合・必要な後続変更まで済んだ成果で判定 |
| 品質と資源の関係 | 同じ締切での品質、全参加者の消費、必要なら総資源を揃えた追試を区別 |
| 探索途中の良い候補 | 診断用。最後に採用できなければ達成成果には数えない |
| 有効な案の多様性 | 診断用。異なる仕組みや失敗条件を持つ、試せる案で確認 |
| 仮説・選択・統合の失敗 | 次にハーネスのどこを変えるかを決める材料 |
| 人数・発話数・review数 | 実行量。成果や能力拡張の代理にしない |

「真に良い案」は、評価者の好む説明や既知referenceへの一致ではなく、公開された価値・制約に対し、
未使用条件で実際に良い成果を出す案として扱う。唯一の最良解が分からない課題では、
明示した到達水準、既知の有効解、性能と費用の比較を使い、世界最適と呼ばない。
自由な発想を一つの模範解答の書式へ閉じ込めない。

## 課題群と当面の優先順位

[難題候補の具体設計](agents/hard-task-candidates.md)で、実装資産・難しさ・評価可能性・不足を分けている。
以下の順序は能力の断定ではなく、今回の着手順のplanning prior。ownerはprimary/integrator。
評価の独立性、準備費、強いsoloの到達状況が根拠と食い違えば更新する。

| 位置づけ | 題材 | 優先する理由・未確定事項 |
| --- | --- | --- |
| 次版を優先 | 継続到着・締切・資源競合・障害復帰を含む実行計画policy | 旧版の参照水準にsolo 2回とも到達。新しい動的課題で難度を広く離して校正する |
| 別系列として保留 | 部分観測下のrobot soccer制御を、未使用状況でも成立させる | 戦術・推定・制御の複数案を実行結果で比べられる。既存simulatorを使えるが、現行の少数seed受入れだけでは不十分 |
| 異なる難しさの確認候補 | 複合障害と互換性を伴う変更系列を診断・修正する | 誤仮説、結合、継続開発を測れる。既知lifecycle欠陥の焼き直しではなく、未解決の要求系列と到達可能な外部評価が必要 |

一つの参照水準が容易だっただけで題材を自動変更しない。まず同じ題材の成果水準と相互作用を十分に広げる。
題材としての改善余地や評価可能性が不足する場合に理由を保存して次候補へ進む。全候補を同時に実装しない。
主評価の難しさを落として小課題へ戻ることを、準備費の節約策にはしない。
短い校正で小課題を使うことと、研究の問いを小課題へ置き換えることを区別する。
外部projectのパスやユーザーによる題材提出は開始条件にしない。

## 実行順と到達条件

旧M0〜M5の運用上の進捗は履歴へ残す。以下のH1〜H5を、今回の能力拡張を目指す主工程とする。

| 段階 | やること | 完了を示す成果・次へ進む条件 |
| --- | --- | --- |
| H1: 高い成果水準と題材の具体化 | 第一候補の公開要求、必要な到達水準、意味ある解法の違い、既存資産の不足を固定 | 実行可能な課題契約と外部評価。最低限動くだけの実装と強い実装を区別し、妥当な別解を受理できる |
| H2: 強いsoloの限界を校正 | 自己検証・再考・複数案・逐次試作を許す。開発用課題で品質と予算の関係、未達の位置を測る | 環境と評価が成立し、到達可能な水準に強いsoloが未達で、協働が変え得る障害の仮説がある。原因の完全な切分けは要求せず、協働結果を見る前に課題系列を採否判断 |
| H3: 到達力を比較 | 同じ課題と公開能力を持つ強いsoloと、目的に応じて協働を選べるハーネスを比較 | 最終成果、全費用、良い候補の有無・選択・統合の成否。必要な機序だけ限定比較で診断 |
| H4: 不足に応じてハーネスを改良 | 案生成、独立性、反証、選択、context、統合、予算配分のうち観測した不足を変える | 版を固定した指示・skill・実行制御と、どの失敗を減らすかの仮説。単なる観測文書の追加で終えない |
| H5: 未使用の難題で再評価 | 同じ協働能力を持つ改良前後のハーネスを比較。強いsoloの基準も保つ | 未使用条件で到達力の改善、退行、費用を評価し、通常の配布へ採否と適用範囲を反映 |

主評価ではAIが難題に応じて相談・独立案・試作比較・検証・分担を選び、継続して開発する。
特定の作用を調べる固定方式比較は、その判断を説明・改善するための補助に置く。
固定事前advisorを全課題の主介入にしない。

一つの実験が有効に終わることと、プロジェクトの目的が達成されることを分ける。
**難題で単独の到達水準を越えられていない間、能力拡張は未達である。**
負の結果で実験を閉じることはできるが、それを目的達成へ読み替えない。

## 実験からハーネスへ返すもの

```mermaid
flowchart LR
    A[高い成果水準と難題] --> B[強い単独の未達を校正]
    B --> C[協働を選びながら探索・実装]
    C --> D[最終成果と全費用を自動評価]
    D --> E[生成・反証・選択・統合の不足を特定]
    E --> F[指示・情報・実行制御を改良]
    F --> G[未使用の難題で改良前後を比較]
    G --> A
```

AIへ渡すのは方式の名前だけではない。どんな停滞に使うか、異なる見方をどう得るか、
何を試作・測定するか、良い候補をどう選ぶか、いつ統合・停止するかまで含める。
未測定の使い方も仮説として試せるようにし、効果の数字と推奨の強さは証拠に合わせる。
小課題で追加費用が増えた事実を、難題で相談や競争を避ける一般規則にしない。

## 過去資産の位置づけ

| 資産 | 維持する用途 | 主評価への制限 |
| --- | --- | --- |
| queue / lifecycle relay | 実行・停止・検証受渡し・原文結合・採点の回帰、低難度対照 | 両側満点を難題への到達力の検証と呼ばない。旧protocolの追加runはしない |
| F12と別評価版 | 構造検査、評価器の誤判定・抜け道の回帰 | 自由な発想や根拠の真偽を測れない現版を主品質評価へ使わない |
| duration atlas | 過去の条件別観測と検索 | primary-only観測を協働効果にしない |
| G2 / soccer / 継続開発の資産 | 難題候補のsource、公開契約、実行評価、過去の探索履歴 | 難度・独立評価・未使用系列の適格性は別途確認する |
| terminal / feedback / agentctl / native contract | 有限実行、所有権、隔離、保全、全費用の回収 | 新しい課題の不足だけ接続。基盤全体の作り直しを前提にしない |
| 配布済みskill / playbook / 実測案内 | 利用入口と範囲付きの証拠 | 配布確認を能力拡張の実証にしない |

過去のrun・protocol・oracle・得点は保持する。
比較の詳細は[協働実験計画](agents/collaboration-experiment-plan.md)、
時計・停止・費用の原則は[評価方針](agents/development-harness-evaluation.md)に置く。
今回の文書改訂だけで、runtime・配布template・モデル能力が改善したとは主張しない。
